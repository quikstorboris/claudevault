# 

Redesigned how the QMS Template Tagging Assistant removes a blank's underscores: live-testing against the real Sumas Mini Storage document showed that padding a removed underscore-run with an equal *count* of spaces (the fix shipped earlier this session) still left fields visibly bunched together, because an underscore glyph is roughly 2x wider than a space in Times New Roman (and likely most fonts) -- character count is not the same as rendered width. User explicitly chose the more-correct-but-costlier fix over an approximate font-ratio hack or defaulting to preserve-blanks mode: keep every original underscore character (guaranteeing exact width, since nothing about the glyph changes) but recolor it white to match the page background, so it reads as blank while still occupying its real space. This required real new capability in docx-surgeon (previously text-splice-only, never touched run formatting): RunSpan now tracks each run's full element bounds (run_start/run_end), its <w:t> opening tag position, and its <w:rPr> range; a new HiddenBlankEdit splits a run into multiple sibling <w:r> elements when it mixes visible label text and hideable blank characters (the real "DATE: _" case -- label and one underscore sharing a run), cloning/augmenting the original <w:rPr> with a <w:color> override (schema-order-aware: color is inserted first, which is safe for every sz/szCs/u shape seen in the corpus) rather than replacing formatting wholesale. tagger-pipeline's to_edit now returns an AppliedEdit enum (Plain(Edit) | HiddenBlank(HiddenBlankEdit)) so the caller can route each confirmed substitution correctly. Critical bug caught only by testing against the real Sumas document end-to-end (not just synthetic unit tests): apply_all_edits initially computed plain-edit and hidden-blank-edit replacements as two independent lists and concatenated them, which panics/corrupts when a plain edit and a hidden-blank edit land in the *same physical run* (common in these templates -- several blanks routinely share one run since Word has no reason to split runs just because a downstream tool would find that convenient). Fixed by unifying both edit kinds into one shared per-run fragment-reconstruction pass (collect_plain_edit_fragments / collect_hidden_edit_fragments / finalize_fragment_replacements) with a regression test reproducing the exact same-run conflict. Verified via a throwaway example run against the actual Sumas .docx (not just fixtures) before shipping -- this is the second time in this session that real-document testing caught a bug synthetic unit tests missed (the first was the original multi-run-blank splice bug); worth continuing to insist on a real-file smoke test as the last verification step before any docx-surgeon change ships. Shipped as commit 2ef0dcf, pushed to origin/main; full workspace test suite (15 suites, 45 in docx-surgeon alone) + clippy clean.
