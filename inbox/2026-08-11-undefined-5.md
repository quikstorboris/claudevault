=== PART 3: PHASE 2 CORE-LOGIC DESIGN, THEN A MAJOR CORRECTION ===
Built unitprep-template-tagger (new pure-logic crate, no I/O, matching the dedup/unit-group convention): detect_candidates(document_text, &[TagValue]) -> Vec<Candidate>, a word-bounded, ASCII-case-insensitive literal-value matcher, deliberately using to_ascii_lowercase (not full Unicode lowercasing) so byte offsets stay valid against the original text even when a value contains non-ASCII letters -- accepted as a cheap tradeoff since accented Latin letters are rare in US self-storage tenant data. 10 unit tests, all passing.

This was originally scoped for a "filled document, known values supplied separately" pipeline (Boris types in or already knows a tenant's real values; the tool finds them in the document to propose tag substitution). Discussion with Boris surfaced that this is NOT the only or even primary real-world case: many client documents are BLANK templates with no values at all, requiring a completely different recognition approach (label-proximity + sentence-pattern templates, recognizing what a blank represents from surrounding text, with no known value to search for). Initially treated these as two separate pipelines needing two separate approaches (Boris explicitly said we'd need both, no strong opinion on build order, and to finalize the already-built one first if anything was outstanding).

Further discussion produced a MAJOR SELF-CORRECTION: the two scenarios actually share ONE recognition engine (label-proximity rules + sentence-pattern templates + shape/regex recognizers for phone/email/zip), just applied in two directions -- on a blank template the anchor is an underscore run to replace; on a filled document the same label/pattern anchors capture the text that's already there and propose replacing it instead. This means fully-automatic recognition without manual OM data entry is achievable via plain rule-based code for anything the pattern library has been taught (labeled forms, known sentence phrasings, shape-based fields) -- NOT AI-only territory, contrary to Boris's initial assumption when he asked directly whether this was "infringing on AI territory." detect_candidates does not become obsolete under this correction -- it becomes a smaller, still-useful component: once the smart recognizer discovers a value once, detect_candidates finds every other occurrence of that same value elsewhere in a longer document. The one real, un-closable-by-rules limit: a document phrased in a way the pattern library has never seen before -- rules can only match explicitly-taught patterns, they can't generalize to novel phrasing the way a language model can. That IS the real AI-territory line, not the recognition problem as a whole. Falls back to the tier-3 human-fallback path when hit, which Boris explicitly said is an acceptable outcome ("chances are there are only so many contract variations... that gap should organically shrink fairly steadily"). Noted the dormant, zero-caller src/ai/interface.rs stub as the pre-existing integration point if that gap is ever worth closing with real AI later -- not needed now.

=== PART 4: DESIGN DECISIONS LOCKED DURING REQUIREMENTS GATHERING (in the order they were settled) ===
- Manual file upload for v1 input; Dropbox-folder read/write integration explicitly deferred ("further down the line, not to worry about now").
- Output: the tool produces a FINISHED .docx with confirmed substitutions already applied -- not a candidate-by-candidate approval screen. The OM reviews one output file, not a list of proposals, consistent with the pre-existing "propose, never modify" hard rule (substituting a literal value for its tag doesn't change legal content, so it's safe to apply directly; only genuine ambiguities get flagged, never auto-corrected).
- Confidence tiers: tier 1 (auto-apply, high confidence), tier 2 (ask via a searchable picker -- plain dropdowns are unusable given the tag count), tier 3 (leave alone, no match). During this dev/testing phase specifically, lean tier 2 over tier 3 for anything uncertain so the picker UI gets exercised across diverse cases; reserve tier 3 for fields confirmed to have no matching tag at all. Boris later said the exact threshold logic is "something that will become clear once I see test results" and explicitly deferred it as non-blocking.
- A NEW risk axis identified beyond tag-choice confidence: composite fields (a date split into day/month/year blanks, or a rent amount split into written-word + numeric blanks) mean some fixes require rewriting non-blank prose, not just filling a blank (e.g. collapsing "the ___ day of ___, 20___" into "{{m.indate}}"). Locked rule: any fix requiring that kind of rewrite always gets flagged for confirmation regardless of how confident the tag choice is -- approved by Boris as the v1 default.
- Scope cuts, all explicit and deliberate: spelled-out/written dollar amounts dropped entirely (almost certainly no QMS tag renders numbers as words); lease-length-in-months dropped (leases are effectively month-to-month in practice); composite-date handling deferred entirely, falling to tier 3 if unclear rather than building special handling now; acknowledgment-initial blanks (scattered "___(initial)" marks) explicitly excluded from the recognizer's scope -- "chances are they are for actual physical signature on a printed contract," Boris's call, even though the later full-corpus tag harvest found a real e.init tag in production use (34 occurrences) that superficially contradicts this -- the exclusion stands as Boris's explicit decision, worth revisiting only if he changes his mind, not something to silently re-open.
- Phone number default rule: when a document has multiple phone-type blanks (Home/Work/Cell) and only one QMS tag exists (e.phone), map the Cell blank to e.phone and leave Home/Work untagged by design ("Not my problem if it's anything else. Welcome to the XXI century." -- Boris's own words). Same default for a single generic "Phone#" blank with no H/W/C breakdown.
- Checkbox/boolean fields (military-status Yes/No, insurance opt-in/opt-out) are explicitly deferred/vaulted for later, not blocking current work, despite being found pervasive across the corpus (see Part 5) -- the tier-1/2/3 design assumes text substitution and has no representation yet for "check this box."
- .doc (legacy binary Word format) support dropped entirely -- OMs will be asked to resave as .docx before uploading; not worth building real binary .doc parsing for what turned out to be a rare case (1 of 9 samples in the early review, later found to be 55 of 662 files -- about 8% -- in the full sweep).
- PDF-as-source-document: discussed at length (PDF->DOCX conversion reliably loses fidelity specifically on page borders/corner marks, shaded text backgrounds, and tab-aligned-rather-than-tabled layouts, since a PDF retains no structural information for a converter to reconstruct -- inherent to the format, not a Rust-specific limitation; rasterizing to an image was ruled out outright since the result wouldn't be a real Word document QMS's merge engine could populate). V1 stays docx-only per earlier agreement; Boris said it's "quite possible we'll drop PDF altogether" -- stored for posterity, not yet decided either way.
- The "+N" date-offset syntax (e.g. {{m.ptd+1}}): initially recommended keeping it as literal enumerated catalog rows (m.ptd+1, l.ptd+1) given that the full corpus sweep found ONLY +1 ever used across 258 real tagged documents (37 and 2 occurrences respectively) -- no +2, +15, or any other value appeared. Boris then reconsidered: QMS separately lets clients create their own EMAIL templates (delinquency notices etc.), and THAT is plausibly where N genuinely varies (5-day, 10-day, 15-day, 30-day notice variants) -- updated recommendation to build +N as a general variable modifier on any date tag, not as one-off enumerated rows, once that work is actually picked up. Implication flagged, not yet acted on: once the general mechanism exists, the already-added m.ptd+1/l.ptd+1 catalog rows become redundant (the base tags m.ptd/l.ptd already exist; a real offset UI would apply +1 to those directly) and should be removed at that point -- not urgent now.
- Table layout handling: strategy is clear (treat each table cell as an independent text region, mirroring paragraph-scoped extraction, rather than flattening a whole row into one string) but not yet implemented in any Rust code.
- .docx parsing/editing: reading strategy was clear from the start; the genuinely open question was whether editing (writing back a change while preserving formatting) could be done reliably -- resolved by actually building and proving docx-surgeon (see Part 6).
- UI design for the review step (once built): a grouped list by confidence tier (Auto-applied / Needs your input / Not recognized), each "needs input" row showing a short in-context text snippet (not the whole document, not just a bare field name) plus the same searchable-dropdown pattern already built for the tag catalog page, with the recognizer's top guess pre-selected. Deliberately deferring the fancier visual document-preview-with-highlighted-spans idea to a later "Phase II, bells and whistles" pass, per Boris's own framing ("let's get the basics working and then put on bow ties, bells and whistles on").
- Tag-catalog growth philosophy, stated explicitly by Boris: "as long as you found at least one [occurrence] in the documents you scan, it deserves a place in the db" -- even tags seemingly unrelated to the template editor (e.g. QMS trigger-tags used only inside QMS's own UI, not in client documents) might deserve tracking for a possible future tool, though none of those turned up in this lease-document-only sweep.

=== PART 6: docx-surgeon CRATE (built, tested, proven against a real document) ===
New standalone workspace crate, explicitly built with an eye toward a possible future open-source contribution -- Boris is "a big fan of FOSS" and wants to vet it first before considering publishing; he asked for a full walkthrough of what that would take (license, README, crates.io publish) in a FUTURE session, not this one. Implements surgical, minimal-diff .docx text editing: given a .docx and a set of exact flat-text-coordinate edits (the same coordinate space unitprep-template-tagger's detect_candidates already returns), produces a new .docx where only those exact spans change and every other byte -- every other run, every table, every style, every other zip part -- is copied through completely unchanged. Deliberately never deserializes the whole document into an object model (the usual approach, and the one that carries real fidelity risk); instead flattens just the plain text while recording each `<w:t>` run's exact byte range in the raw XML (read.rs::extract_flat_text, a streaming quick-xml walk), then splices edits directly into the original bytes at that exact range (edit.rs::apply_edits). The one real correctness subtlety handled deliberately: never slices raw XML mid-entity (an encoded run like "Smith &amp; Sons" has a different byte length than its decoded form "Smith & Sons") -- always replaces a touched run's entire raw content wholesale after a decode-splice-reencode round trip in decoded space, making entity corruption structurally impossible rather than merely avoided by careful offset math. Refuses (does not guess at) an edit spanning more than one run, matching the project's established "flag conservatively, don't guess" philosophy everywhere else.

20 tests total: 18 unit tests (in read.rs and edit.rs) plus 2 integration tests proving the surgical claim against a REAL document, not a synthetic fixture -- Atherton Storage's actual blank lease template (no tenant PII, safe to commit; committed as docx-surgeon/tests/fixtures/atherton-storage-contract.docx, matching the precedent already set by the dedup tool's own real-facility-data fixtures). The integration tests verify (a) every zip entry other than word/document.xml is byte-identical between the original and edited file, and (b) within document.xml, everything outside the one targeted run's own text content is byte-identical too. Additionally, and not something automated tests alone would prove, manually verified via Word COM automation (Word happens to be installed on this Windows machine) that the actual edited output opens cleanly in real Microsoft Word with no repair/corruption prompt, and the substitution renders correctly. cargo fmt/clippy/test all clean.

Committed as f590801 (crate) plus a follow-up 569e895 fixing a stray Dropbox metadata sidecar file (":com.dropbox.attrs") that leaked into the fixture commit via the Windows/Dropbox file copy -- caught and cleaned up before it mattered, not left in the repo. NOT YET WIRED into any pipeline, HTTP endpoint, or the template-tagger crate -- built and proven fully standalone first, same sequencing already used for detect_candidates.
