# 

Significant design correction on the QMS Template Tagging Assistant: the "blank template" and "filled document" input scenarios are NOT two separate recognition pipelines needing separate approaches -- they share one recognition engine (label-proximity rules, sentence-pattern templates, shape/regex recognizers for phone/email/zip), just applied in two directions. On a blank template the anchor is an underscore run to replace; on a filled document the same label/pattern anchors capture the actual already-present text to propose replacing with a tag instead. This means fully-automatic recognition without manual OM data entry is achievable via plain rule-based code for anything the pattern library has been taught (labeled forms, known sentence phrasings, shape-based fields) -- not AI-only territory, contrary to Boris's initial assumption. detect_candidates (the literal-value matcher already built) doesn't become obsolete under this correction -- it becomes a smaller, still-useful component: once any value is discovered once by the smart recognizer, detect_candidates finds every other occurrence of that same value elsewhere in a longer document. The one real, un-closable-by-rules limit: a document phrased in a way the pattern library has never seen before -- rules can only match explicitly-taught patterns, they can't generalize to novel phrasing the way a language model can. That's the actual AI-territory line, not the recognition problem as a whole. Falls back to the already-designed tier-3 human-fallback path when hit, which Boris has already said is an acceptable outcome, not a failure. Noted the dormant, zero-caller src/ai/interface.rs stub in unitprep-api as the pre-existing integration point if/when that gap ever gets worth closing with real AI -- not needed now.

Also applied migration 20260810150000 (committed 1a4a662, not yet pushed): added e.dob, e.add1, e.add2 to client_ops.qms_tag, all confirmed directly against the live QMS tag picker. e.address (single-line) was already seeded from the original 13; add1/add2 are the two-line variant and are independent 1:1 tag mappings, not a composite-field case like the date splitting.
