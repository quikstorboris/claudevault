# 

Locked scope decision for QMS Template Tagging Assistant Phase 2 (rule-based candidate detection), 2026-08-10: build core logic now, scoped narrowly. (1) Only propose substitutions for unambiguous, already-confirmed literal-string tags -- name, address, phone, email, DL#, unit number, the "easy cases" named in the original design note -- explicitly excluding anything flagged uncertain (the m.*/l.* duality, the d.* overload, the {{sig}} vs /s/{{e.name}} signature question) rather than guess and risk a wrong tag reaching the output document. (2) Skip building the deferred qms_template_context/join-table schema. Boris's QuikStor dev-team channel is gated behind his CTO right now, but context-scoping doesn't actually need QuikStor -- it's a "check the live QMS UI yourself" question, not a developer question -- so if/when context disambiguation is ever needed it should be a manual per-run input from the OM, not a DB schema, and only gets built once the catalog actually grows a colliding pair (none of the current 13 seeded tags collide, so this isn't needed yet either). Catalog-size concern (13 vs 221+) explicitly not treated as a blocker -- grow it organically the same way the 6 new families got found, by hand from real documents.
