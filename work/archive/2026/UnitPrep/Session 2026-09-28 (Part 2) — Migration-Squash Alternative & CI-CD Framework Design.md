# Session 2026-09-28 (Part 2) — Migration-Squash Alternative & CI/CD Framework Design

Continuation of the same day's [[Session 2026-09-28 — client_ops Schema Split, Runbook, Live-DB Audit & CI Backlog|earlier work]], prompted by two things landing back to back: Boris reacting to a pasted CTO-level board assessment of UnitPrep (strong on engineering quality, sharp on bus-factor/operational-continuity risk, and explicitly naming "large schema cleanup theater" as a trap to avoid right now), then asking to resolve the migration-squash backlog item without losing history, then — because CI/CD had come up in effectively every outside review without ever being properly designed — asking for a full CI/CD framework brought in from outside best-practice knowledge, not just what he already knew from past projects (local `.sh` pre-push scripts).

## Migration squash rejected in favor of a generated schema snapshot

Investigated the actual 86-migration history before acting (per [[Dev Principles]] #12): no thrash, no abandoned dead-ends, just a long but healthy incremental record — the most-touched tables (`process_street_settings` ×9, `facilities`/`companies` ×6) are legitimate feature growth, not backtracking. The problem a squash was chasing was pure onboarding readability, not correctness or risk — and a real squash would mean reconciling the dev DB's already-applied migration history against an incompatible new file set (full reset or fragile manual reconciliation), for zero functional benefit, while destroying the granular "how did we get here" trail.

**Chosen instead**: `SCHEMA.sql` — a `pg_dump --schema-only` snapshot checked into the repo root, a point-in-time reference doc, not `sqlx`-applied, regenerated by hand after schema-changing migrations. Solves the actual readability problem completely at a cost of one metadata-only read (no data, no writes — confirmed cheap enough to run immediately rather than waiting for the compute budget to reset, unlike the DB-touching work earlier this same day). **This fully closes the migration-squash item** — nothing left to revisit later, since the concern is now solved a different, safer way. Full reasoning in [[Key Decisions]].

## CI/CD: a tiered framework, designed in full, built in part

Wrote the complete design to `reference/UnitPrep CI-CD Framework.md` — the living policy doc, meant to be followed rather than re-derived each time it comes up. Key moves:

**The shaping constraint**: 100+ commits/month, solo, direct-to-`main`. A CI design that makes every push wait on a slow Rust test suite doesn't add safety, it pressures shipping into fewer, larger, riskier batches — the opposite of the goal. Every tier is built around "cheap and fast enough to never be worth skipping."

**Tier 0 (built, shipped this session)**: `scripts/preflight.sh` in both repos — fmt/clippy/fast-test-suite/version-consistency/secret-pattern-scan, run before pushing (not before every commit, matching this project's own "batch, don't checkpoint" cadence). Deliberately never runs `#[ignore]`d real-DB tests, so it can never spend Neon compute. The version-consistency check directly closes the gotcha from [[Session 2026-09-24 — Grok Review Follow-Through — CHANGELOG Backfill, 5-File Split & Cancel-Progress UI|earlier this week]] (a real batch shipped with no version bump, caught only by accident). Tested for real, not just written — caught the 3 pre-existing clippy warnings that had been sitting in the codebase all session, fixed them (2 trivial `sort_by`→`sort_by_key`, 1 `#[allow(clippy::too_many_arguments)]` with justification rather than a struct-bundling refactor for a genuinely-8-field form-edit function), then re-ran clean. Shipped as `unitprep-api v1.9.41`, `unitprep-ui v1.6.41`.

**Tier 1 (designed, `.github/workflows/` deliberately not created yet)**: split by cost, not by repo — `cargo check` (type-check only, no codegen/linking, dramatically faster than `cargo test`) plus fmt/clippy/`tsc`/`eslint` on every push as a cheap backstop for Tier 0; the full, slower test suite only on a version-tag push, which naturally throttles the expensive gate to actual release cadence instead of per-commit. The one piece of outside best-practice knowledge worth calling out specifically: **GitHub Actions service containers** — a throwaway Postgres spun up fresh per CI job, migrations replayed against it, torn down after. This means the project's real-DB integration tests (session durability, RLS shape) *can* run in CI without ever touching Neon or spending its scarce compute budget — not a future nice-to-have contingent on more resources, available today whenever Tier 1 gets turned on.

**Tier 2 (designed, dormant until a second developer)**: a `dev` branch (already anticipated in [[Patterns]]'s branch-policy entry from 2026-07-23), branch protection, required PR review, the ephemeral-Postgres suite becoming a required check, scheduled (not per-push) `cargo audit`/`gitleaks`.

**Explicitly deferred within Tier 0 itself**: a real secrets-scanning tool (`gitleaks`) and dependency-vulnerability scanning (`cargo-audit`) — the preflight scripts ship with a narrow grep-based secret-pattern check today (private key headers, common cloud-key prefixes, literal password/secret assignments), clearly labeled as a backstop, not a substitute. Both real tools are a one-time, no-sudo-needed install away whenever it's worth doing.
