## Core & unit-group crates — fully resolved

All findings fixed, verified with `cargo build`/`test`/`clippy` after each batch; workspace `cargo fmt --check` reports 0 diffs for these two crates specifically.

- **`cargo fmt`** applied to `core` and `unit-group` (312 of the workspace's 808 diff hunks) — mechanical, no logic change.
- **`unit-group/src/analysis/mod.rs` `analyze_batch`** — removed 4 unnecessary full-collection clones (`advisory_issues`, `global_groups`, `facilities`, `reference_groups`) by destructuring the owned `BatchRun` directly instead of cloning fields then discarding the original.
- **`unit-group/src/validation/mod.rs` `RowScan`** — added a `group_fingerprints: HashMap<String, (bool, GroupFingerprint)>` cache + `group_fingerprint()` helper method, so `is_odd_group_name`/`parse_fingerprint` compute once per distinct group name per document scan instead of once per row (a 10k-row file with 50 distinct groups previously did up to 20k fingerprint parses instead of 50).
- **`unit-group/src/corrections.rs` `apply_corrections`** — was O(rows × corrections), rescanning the whole corrections map per row; now builds a `by_unit: HashMap<&str, Vec<(&str,&str)>>` index scoped to the document's own `file_name` first, then does O(1) lookups per row.
- **`unit-group/src/models.rs`** — deleted the dead, silently-lossy `impl From<&str> for Severity` (no call site anywhere in the workspace constructed one; it also mis-mapped uppercase `"ERROR"` to `Info`). Deleted the `pub type Issue = AdvisoryIssue` alias — the crate was exporting both names publicly and different consumers had drifted onto different ones (`analyze.rs` used `AdvisoryIssue`, `csv_export.rs` used `Issue`). Consolidated on `AdvisoryIssue` everywhere: `models.rs`, `lib.rs`'s re-export list, `analysis/mod.rs`'s import + construction site, and (necessarily, to keep the workspace compiling) `src/infrastructure/csv_export.rs`'s import + 2 function signatures — the one edit in this batch that reached outside `core`/`unit-group` proper, unavoidable since it's the same public type.
- **`core/Cargo.toml`** — narrowed `tokio` from `features = ["full"]` to `["rt", "time"]` (verified only `tokio::spawn` + `tokio::time::interval` are used anywhere in `core`, no `#[tokio::test]`/`#[tokio::main]` macro usage to justify keeping `macros`).

Verification after every batch: `cargo build --workspace` clean, `cargo test --workspace` — 267 tests passing (64 in unit-group specifically), `cargo clippy --workspace --all-targets` — identical 17 pre-existing accepted auth-WIP warnings, zero new ones.

**Deliberately NOT done**, by choice, per Boris's explicit instruction to prioritize simplicity/elegance over restructuring: did not decompose `analyze_batch` into named helper sub-functions (the audit flagged this as a low-priority "nice to have" alongside the clone fix; judged that further restructuring a function that was otherwise correct, right after a mechanical clone fix, added risk without a proportionate elegance win — left as a future opportunity if `analysis/mod.rs` grows further).

## M1 — Session ownership

- `core::session::SessionMetadata` gained `owner_id: Option<Uuid>` (`core` now depends on `uuid` too, matching the binary's existing `features = ["v4"]`). `SessionMetadata::new` takes `owner_id` as its 2nd param.
- `SessionStoreExt` (core/src/session_store.rs) gained `with_owned_session`/`with_owned_session_mut`, sitting next to the existing `with_session`/`with_session_mut` — looks up by id as before, then returns `None` (not a distinct 403-shaped error) if `metadata().owner_id != Some(caller_id)`, so a session belonging to another user is indistinguishable from one that doesn't exist.
- Threaded `owner_id: Option<Uuid>` all the way from the two session-creating HTTP handlers (`src/api/upload.rs`, `src/api/dedup.rs`) through `SessionService::create_session` / `DedupSessionService::create_session` through `Session::new` / `DedupSession::new` to `SessionMetadata::new`. Both handlers currently pass a literal `None` (no `AuthenticatedUser` on either yet) — the point is that wiring auth in later is "change `None` to `Some(user.id)` at 2 call sites + add `user: AuthenticatedUser` to 2 handler signatures," not a data-model change made under time pressure.
- Added 5 new unit tests in `core/src/in_memory_session_store_tests.rs` covering: matching owner succeeds, mismatched owner returns `None`, nonexistent session returns `None`, a session with no owner (`None`, today's normal case) can't be claimed by anyone, and the `_mut` variant enforces the same gate.
- **Explicitly not done, on purpose**: none of the ~20 existing HTTP handlers were changed to call `with_owned_session` instead of `with_session` — that's meaningless before `AuthenticatedUser` actually exists on those handlers, and is really the first step of the auth-wiring work itself, not of this cleanup pass.

Verified: `cargo test --workspace` (269 passing), `cargo clippy --workspace --all-targets` (same 17 accepted auth-WIP warnings, zero new), `cargo fmt -p unitprep-core -- --check` (0 diffs).

**Process note for future sessions**: mid-fix, a `perl -0777` regex meant to mechanically append `, None` to ~21 test call sites got mangled crossing the Git Bash → `wsl.exe` → WSL bash quoting boundary and silently deleted the arguments instead. Caught immediately by the next `cargo build`, fixed by `git checkout --` on the affected files (confirmed via `git diff --stat` that only the corrupted mechanical edit was on those files) and redone with direct `Edit` calls instead of another cross-boundary regex. Reinforces the existing rule: write multi-step or regex-bearing shell work to a script file first, never inline through the `wsl.exe` boundary, even for something that looks simple enough to be "one command."

## M2 — Dedup crate

All 8 findings from the audit fixed same session as M1, each with a new regression test:

- **`dedup/src/comparison.rs` `field_matches_across`** — now compares `(is_empty(raw), normalize_value(kind, raw))` instead of just the normalized value, so a garbage phone value ("N/A", "----") that normalizes to the same `""` as a genuinely blank one no longer silently matches it. `distinct_display_values` (same file) got the identical `(bool, String)` key treatment, now also taking `spec.kind` as a parameter, so case-variant values (e.g. `"Bob@Test.com"` vs. `"bob@test.com"`) collapse into one displayed value instead of two.
- **`dedup/src/relatedness.rs` `full_address`** — stopped filtering blank address sub-fields out before joining; every field keeps its position in the join now, blank or not, so two addresses whose data lands in different columns (a real vendor-format inconsistency, not contrived) can no longer collapse to the identical joined string.
- **`dedup/src/phrasing.rs` `units_by_value`** — same `(is_blank, normalized)` key fix as `comparison.rs`, so `describe_field`'s generated note sentences merge differently-formatted-but-equal values (e.g. two phone numbers) into one clause instead of overstating how many distinct values actually disagree. Needed a new `types::kind_for(FieldName) -> FieldKind` lookup (added to `types/fields.rs`, re-exported from `types.rs`) since this call site only had a bare `FieldName`, not a full `FieldSpec`.
- **`dedup/src/types.rs` `title_case`** — split into `title_case` (splits on whitespace) + new `title_case_word` (capitalizes the first letter *and* the letter immediately after any `'`/`-`, lowercasing everything else) — `"O'BRIEN"` → `"O'Brien"`, `"SMITH-JONES"` → `"Smith-Jones"`, instead of only the word's very first letter ever being capitalized.
- **`dedup/RULES.md:126`** — replaced the stale "plain fields (phone, email, names): lowercase + trim" bullet with a separate `Phone` entry describing the real digits-only normalization.
- **`dedup/src/note_composer.rs`** — tests extracted to new `note_composer_tests.rs` via `#[path]`, matching `relatedness.rs`'s existing convention (file dropped from 318 to ~167 lines).
- **`dedup/src/report.rs` `find_typo_variant_candidates`** — hoisted `let a = groups[i].records[0].display_name()` (and its blank-check) above the inner `for j` loop — it only depends on `i`, so it was being recomputed needlessly once per `(i, j)` pair instead of once per `i`.
- **New synthetic full-pipeline test** — `report.rs`'s test module gained `full_pipeline_runs_all_three_passes_together_on_fabricated_data`, a fabricated (no real PII) 5-record fixture exercising grouping → flagging → typo-variant → relatedness together in one `run()` call — closes the gap left by the two `#[ignore]`d real-PII fixture tests in `tests/reference_fixtures.rs`, which don't run in CI.

Verified: `cargo test --workspace` (277 passing, 48 in `unitprep-dedup` specifically — up from 40 baseline + 8 new regression/pipeline tests), `cargo clippy --workspace --all-targets` (same 17 accepted auth-WIP warnings, zero new), `cargo fmt -p unitprep-dedup -- --check` (0 diffs).

## M3 — API / session / export layers

(`src/api/`, `src/application/`, `src/infrastructure/`; `src/auth/*` excluded — WIP, tracked separately)

- **`api/mod.rs`** — added router-wide panic-catching middleware: `tower_http::catch_panic::CatchPanicLayer::custom(handle_panic)` as the outermost layer, where `handle_panic` logs the panic payload via `tracing::error!` and returns the project's own `ApiErrorBody` 500 shape instead of dropping the connection. Added `tower-http`'s `catch-panic` feature. 3 new unit tests (`&str` payload, `String` payload, an unrecognized payload type — `std::panic::panic_any` isn't limited to strings) proving the handler itself never panics while handling a panic.
- **`infrastructure/csv_export.rs`** — added a shared `write_csv(header, rows)` helper; the 4 functions that actually used `csv::Writer` (`generate_net_new_groups_csv`, `generate_facility_assignments_csv`, `generate_facility_group_lookup_csv`, `generate_advisory_csv`) now call it instead of each repeating the writer/flush boilerplate. (The other 2 `generate_*` functions the prior review counted are JSON, not CSV — they don't share this boilerplate and were left alone.)
- **`dedup_csv_export.rs` / `dedup_xlsx_export.rs`** — added `record_field_values(&TenantRecord) -> [&str; 25]` and `NOTE_COLUMN_INDEX` to `dedup_export_plan.rs` (the crate's own designated "shared source of truth for row/column layout"); both writers now call it instead of independently enumerating the same 24 fields. Verified byte-identical output via the existing CSV/XLSX export tests (all 5 passed unchanged).
- **`discover/dto.rs`** — added `impl From<&DiscoveryResult> for DiscoverResponse`, filling every field the two types share (deriving `unit_files_found`/`group_files_found` from `discovery` rather than defaulting them, since those two actually are derivable); the ~8 fields `DiscoverResponse` needs that `DiscoveryResult` doesn't carry (`discovered_group_names`, `group_file_confirmed`, etc.) are set via struct-update syntax at the one call site in `discover/compute.rs`, replacing ~60 lines of hand-copying with ~15.
- **Stale `unit_file_upload` doc references** — fixed in `unit_group_session.rs`, `manual_file_upload.rs`, `group_file_upload.rs`: reworded to describe reality (one real endpoint today, `manual_file_upload.rs` kept as reusable-shaped plumbing for a *possible* future second one, not a currently-existing sibling).
- **`Session::effective_documents_for(names)`** added alongside the existing `effective_documents()` (both now share a private `effective_documents_matching(predicate)`); repointed `analyze.rs` (filters to the union of unit + group file names, since it needs both for `select_group_document`), `validate.rs` (unit files only — the now-redundant post-filter inside its loop was removed too), and `discover/compute.rs`'s `compute_discovered_group_names` (unit files only) to filter *before* the mapping/correction/exclusion transform instead of after.

- **`src/api/upload_tests.rs` added** — the one handler with zero coverage now has 4 tests, built by constructing a real `multipart/form-data` request body and driving it through axum's own `Multipart::from_request` (no new dependency needed — `axum`'s `multipart` feature and `tokio`'s `full` features, both already present, are sufficient): rejects when nothing uploads successfully, a single real file, a field with no filename counted as failed without blocking a valid file in the same upload (the specific partial-failure path the audit called out), and multiple real files all counted.

## M4 — unitprep-ui frontend

- **`ScanResultsPage.tsx`** — the hand-rolled `/validate` effect replaced with `useSessionPost<ValidateResponse>(sessionId, "/validate")`. Since the page also needs to *mutate* results after later actions (`handleResultsUpdated`, unlike a plain read-only hook consumer), the design is: `results = resultsOverride ?? fetchedResults` — a `null`-until-set local override wins over the hook's own `data`, computed fresh every render with no effect needed to copy hook data into local state (which would itself violate the project's no-setState-in-effect convention). Session-expiry is combined the same way: `sessionExpired = fetchSessionExpired || actionSessionExpired`.
- **3 discovery components migrated onto `useSessionAction`**: `UnitFileSelectionSection.tsx` (1 fetch → 1 hook), `MasterGroupFileSection.tsx` (2 of its 3 fetches — confirm, select-candidate; the manual file-upload handler stays hand-rolled on purpose, see below), `FormatConfirmationSection.tsx` (2 fetches sharing one endpoint → 1 hook instance, since confirm/map/reset button sets are mutually exclusive in the UI so sharing one pending/error pair is safe). **Deliberately NOT migrated**: `MasterGroupFileSection.tsx`'s manual group-file upload — it POSTs `FormData` (a real file), not JSON; `useSessionAction` is JSON-only by design (matches every other real caller in the app), so forcing this one onto it would mean changing the hook's contract for a single call site. Left as its own hand-rolled fetch with local `manualGroupFileUploading`/`manualGroupFileError` state, same as before.
- **`credentials: "include"` + 401 handling added to the two shared hooks** (`lib/useSessionPost.ts`, `lib/useSessionAction.ts`) — a 401 is folded into the exact same `sessionExpired` result/state a 404 already produces (no dedicated login-required UI exists yet to route a 401 to instead; "start over" is the correct behavior for both today). Inert until auth actually issues a cookie, but this is now genuinely a 2-file change to activate rather than a grep-and-patch — the ~6 remaining raw `fetch()` sites (multipart uploads, `useDiscoveryFlow`) are *not* covered by this and would still need their own patch when auth lands, exactly as the audit anticipated.
- **`MasterGroupFileSection.tsx` split** (517 → 381 lines): extracted `GroupFileCandidatePicker.tsx` (104 lines, the radio-button picker) and `GroupFileSummary.tsx` (118 lines, the format-status + confirm/choose/select-different actions).
- **`FormatConfirmationSection.tsx` split** (521 → 223 lines): extracted `FormatResolutionActiveView.tsx` (341 lines, the confirm/map UI) and `FormatConfirmedSummary.tsx` (89 lines, the read-only confirmed state).
- **`ScanResultsPage.tsx`**: `deriveScanResults(...)` wrapped in `useMemo` keyed on `[results, reasonSnapshots, excludedGroupNames, acknowledgedGroupNames]` (safe alongside the page's existing setState-during-render blocks, since a state change there triggers a synchronous re-render that recomputes the memo with the new deps, same as any other `useMemo`). The 5-tile stat grid (Files Checked/Errors/Warnings/Files Errored/Export Status) extracted to `components/scan-results/ScanResultsStatTiles.tsx` (687 → 588 lines).
- **Important correction to the record, found by actually trying to add the "2 custom ESLint rules"**: don't add them — **they already exist**, just not as project-authored code. `eslint-plugin-react-hooks@7.1.1` (bundled transitively via `eslint-config-next`, part of the newer React-Compiler-era "rules of hooks" set) ships `react-hooks/set-state-in-effect` and `react-hooks/refs`, which do exactly what "no setState in effects"/"no ref.current during render" describe — confirmed by writing a deliberate two-violation scratch file and running `eslint` on it: both official rules fired immediately, with zero config changes needed, because they're already active by default. A from-scratch custom plugin (`eslint-rules/no-effect-only-set-state.js`, `no-ref-current-during-render.js`) was written, verified to correctly produce zero false positives against the entire real codebase, verified to correctly catch the same scratch violations — then **deleted**, since duplicating an already-correct, better-tested official rule with a hand-rolled heuristic is exactly the unnecessary complexity this whole audit is trying to remove, not add. Net result: this punch-list item needed no code at all, just confirmation it was already covered. Both the original review's claim ("2 custom ESLint rules") and this audit's own prior correction ("false, not tooling-enforced") were wrong in the same way — neither checked whether the *bundled* config already covered it before concluding it wasn't enforced.

Verified: `tsc --noEmit` and `eslint .` clean across the entire repo after every change (checked incrementally per file, then once more at the end). Committed and pushed 2026-07-28 as part of `unitprep-ui`'s v1.1.1 — see [[Post-Refactor Audit - Shipped as v1.1.1]].

## M5 — Dependency audit specifics (Rust side)

**Rust (`unitprep-api`) — fully clean.** Installed `cargo-audit` (v0.22.2, wasn't present). First run found 5 issues:

- `quick-xml` 0.36.2 (direct dependency, `core/Cargo.toml`) — two High (7.5) RustSec advisories (RUSTSEC-2026-0194 quadratic-time duplicate-attribute checking, RUSTSEC-2026-0195 unbounded namespace-allocation DoS), both **directly reachable via a user-uploaded file** (this crate parses uploaded SpreadsheetML). Fixed: bumped to `quick-xml = "0.41"`. Required two source changes in `core/src/parsing/spreadsheetml.rs` — 0.41 split the old one-call `unescape()` into a charset-decode step (`decode()`) plus a separate entity-unescape step (`quick_xml::escape::unescape()`), and deprecated `Attribute::unescape_value()` in favor of `normalized_value(XmlVersion::Implicit1_0)`. All 4 SpreadsheetML tests + the full 284-test suite still pass unchanged.
- `quick-xml` 0.31.0 (transitive, via `calamine` 0.25.0) — same two advisories. Fixed by bumping `calamine` from `"0.25"` to `"0.36"` in *both* places it was pinned (`core/Cargo.toml` and, easy to miss, the root `Cargo.toml`'s own separate `[dev-dependencies] calamine = "0.25"` entry used only to read back xlsx-export test output). An 11-minor-version jump sounded risky (especially right after this session's own Excel date-parsing changes to `core/src/parsing/excel.rs`) but compiled and passed the full test suite with **zero code changes needed**.
- `rsa` 0.9.10 — Medium (5.9), Marvin Attack timing side-channel, **no fixed upgrade exists in the rsa crate itself**. Traced via `cargo tree -i rsa --target all` (empty output) to `sqlx-mysql`, an optional sub-crate `sqlx` still resolves into `Cargo.lock` even though this workspace only enables sqlx's `"postgres"` feature, never `"mysql"` — confirmed via a from-scratch `Cargo.lock` regeneration producing a byte-identical file, i.e. not a stale/orphaned entry, just an unavoidable quirk of how sqlx's own `Cargo.toml` structures its optional backends. No rsa code is ever compiled into the binary. Documented as an accepted, non-reachable finding in a new `.cargo/audit.toml` (`ignore = ["RUSTSEC-2023-0071"]`, with the full reasoning in a comment) rather than left as a recurring unexplained "vulnerability found" error.
- Also ran a plain `cargo update` first (safe, semver-respecting), which incidentally fixed a `spin` yanked-crate warning (0.9.8 → 0.9.9, via `multer`/`axum`).
- Final state: `cargo audit` exits clean, 0 findings.
