**2026-10-05 (night) - B3 done (api v1.9.73, local; push pending); B5/B6 analyzed.** `9e1eb76` + `95465f6`, tag `v1.9.73`. See the B3 spec amendment above for the design and numbers.
- **B5 analysis (session persistence) - recommend NO CODE CHANGE.** After A4/A5 every heavy `save()` (session create, `set_unidentified_mode`) already runs inside a blocking closure, so the original "serialize inline" complaint is gone. What remains: (a) unordered upserts - two saves of one session within milliseconds are essentially impossible in practice (a save happens at creation and again only on a user clicking "unidentified mode", seconds apart); (b) payload size (a dedup session persists both `records` and the derivable `report`) - trimming it changes the bincode shape, which makes any in-flight persisted session unreadable after a deploy; sessions live minutes-hours, so low harm but nonzero, for a saving that only matters on session creation; (c) unit-group mutating handlers never `save()`, so a server restart mid-session restores the state as of creation (a design gap, not a performance one - decision for Boris whether sessions should survive restarts at all beyond creation); (d) `last_accessed` in Postgres only moves on `save`, so the Postgres sweep can expire a row for a session still active in memory (matters only if the server restarts mid-session). Recommendation: close B5; if (c)/(d) bother you, they are a small separate "session durability" task, not a performance one.
- **B6 analysis (`create_dedup_run` off the response path) - recommend WON'T DO.** A6 already moved the CPU part (sealing) off the workers and out of the transaction; what is left inline is BEGIN + `set_config` + INSERT + COMMIT, about 4 round trips (~80 ms at Neon-like latency) on a check that takes seconds. Spawning it makes the response return before the row exists, and `attach_output_bytes`/`attach_output_dropbox` (called by export) are plain `UPDATE`s that affect ZERO rows - silently, no error - if the row is not there yet; a fast export click (or a scripted flow) would lose its stored output. `client_ops/tool_runs.rs` documents exactly that silent-zero-row failure class from 2026-09-10. Not worth ~80 ms. If ever wanted: make export retry/wait for the row, or insert-if-absent from the attach path.
