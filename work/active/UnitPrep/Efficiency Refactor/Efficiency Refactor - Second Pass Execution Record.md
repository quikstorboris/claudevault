## A1 / S1: ClickUp fan-out (decision)

Checked each call site rather than trusting "raw `join_all`":
- `clickup_copy/copy.rs`: chunks by `WRITE_CONCURRENCY` then `join_all` inside the chunk.
- `clickup_copy/exec.rs`: `CHUNK_SIZE = 4`.
- `clickup_copy/bulk.rs`: `LIST_READ_CONCURRENCY`.
- `clickup/tasks.rs` `list_tasks`: a page batch of `FIRST_PAGE_BATCH = 2`, then `LATER_PAGE_BATCH`, capped at `MAX_TASK_PAGES = 30`.
- Every ClickUp call also goes through the per-user limiter `clickup::rate_limit::for_user`.
- The only other raw `join_all`s are the two in `clients_clickup_links.rs` (lines ~285, ~412): **audit-log DB writes after the transaction commits**, not ClickUp calls.
`join_all_bounded` fixes the cap at 6 (`MAX_CONCURRENT_UPSTREAM_CALLS`) and is built for Process Street's hourly quota. Forcing ClickUp onto it would change its throughput for no measured benefit. **Decision: leave as is.** Revisit only if ClickUp starts returning 429s in production.

## A2: XLSX export

`dedup_xlsx_export.rs` called `Format::new()` once per data row. It now builds `cluster_formats` (one per `CLUSTER_COLORS` entry, four) before the loop and indexes by `cluster % len`; output identical (existing XLSX tests pass). Context: XLSX is the one slow dedup stage (154 ms release at 5,000 rows, 1.2 s debug) and already runs on the blocking pool via `api/dedup_blocking.rs` -> `generate_export`.

## A4: transactions vs ClickUp HTTP (audit)

Read the ordering, no violation found:
- `clickup_copy/bulk.rs::prepare_bulk`: begin RLS tx -> two reads -> commit -> only then ClickUp.
- `clickup_copy/jobs.rs`: every transaction is a short single-purpose begin/commit.
- `clickup_connection.rs`: `identify` (HTTP) runs before the save transaction and after the commit, never inside.
- `clickup_run_update.rs`: the transaction (lines ~194-250) contains no HTTP; Dropbox/ClickUp calls come later.
The rule is now written in the `clickup_copy` module docs. A structural test was considered and rejected: ordering of `.await`s inside a function is not reliably checkable by a test, and a wrong test is worse than a comment.

## B1: Tagger parsed-document cache (measured, not built)

`report.rs` and `apply.rs` re-run `read_docx` on the stored bytes. New ignored test `docx-surgeon/tests/read_docx_timing.rs` (release, 50 runs after a warm-up):

| Fixture | Size | `read_docx` p50 | p95 | max |
|---|---|---|---|---|
| `atherton-storage-contract.docx` | 18 KB | 0.46 ms | 0.79 ms | 2.24 ms |
| `longview-self-storage-rental-agreement` (`tagger-pipeline` corpus) | 48 KB | 3.96 ms | 8.59 ms | 15.9 ms |

Command: `cargo test --release -p docx-surgeon --test read_docx_timing -- --ignored --nocapture`. Parsing is already off the async workers (`run_blocking`). A cache would keep a parsed document (several times the bytes) in memory per session and cannot go into the durable bincode session. **Decision: do not cache.** Revisit only if templates grow by an order of magnitude or the UI becomes chatty.

## C-A, C-C, C-D: ops documentation and tooling (RUNBOOK + code)

- **RUNBOOK "Database pool and load"**: the measured 1/4/8/16-operator table (canary p50/p95/p99, dedup check p50/p95, checks per second, peak pool use), the 2-worker and inline A/B results, and the remote-database sizing rules.
- **`DB_POOL_MAX_CONNECTIONS`** (new env var, `db.rs`): default 20, accepted 1-200, anything else falls back to 20 (a bad value never fails startup; the pool is lazy). Unit-tested (`the_pool_size_comes_from_the_environment_within_bounds_else_the_default`). Sizing rules: watch for `PoolTimedOut` (10 s acquire timeout), raise in steps of 10, never exceed the database's client limit across all instances, rerun `concurrent_load_report` through `dev-tools/latency_proxy.py --delay-ms 10` after any change. With a 20 ms round trip the pool saturates (20 of 20) at 8 operators before the CPU does.
- **Retention (C-C)**: `client_ops.tool_runs` is kept indefinitely; a 2,400-row dedup run stores about 1.9 MB (encrypted source ~272 KB + encrypted records ~1.6 MB), so 1,000 runs is about 1.9 GB. New read-only `scripts/tool_runs_storage.sql` reports size by tool and by age plus total table size (tested against the empty local test-db; needs a role that can read the table through RLS or it under-reports). **No policy was implemented and nothing deletes data**: dropping stored records removes a facility's history and re-match ability, a business decision. Decide before stored runs pass ~500 or before the cloud move (the memory note `project_cloud_move_triggers`). Options in RUNBOOK: keep everything; after N days keep only summary + output; archive to cold storage.

## Gotchas found (also copied to [[Gotchas]])

- **WSL Chromium without sudo**: needs `libnspr4`, `libnss3`, `libasound2t64`; `apt-get download` them, `dpkg -x` into `~/pwlibs/root`, run with `LD_LIBRARY_PATH=~/pwlibs/root/usr/lib/x86_64-linux-gnu`. `npx playwright install-deps` needs sudo and hangs.
- **git worktree + `node_modules`**: a symlink to the main checkout's `node_modules` breaks Turbopack (`find_package` resolve failures); use `cp -al` (hardlinks, instant) instead.
- **Windows `git` on a `\\wsl.localhost` path** flipped executable bits (`.githooks/pre-push`, `scripts/*.sh`) and rewrote files as CRLF; run all git commands inside WSL, and fix with `chmod +x` + `git checkout --`.
- **Releasing beside another session's uncommitted work**: build the release in `git worktree add --detach <path> origin/main`, copy only your files in, run preflight there, commit/tag/push with `HEAD:main`; then in the main checkout `git reset --mixed <sha>` (working tree untouched) and, for files only you changed, `git checkout -- <file>` from WSL git.
- **`cargo audit` can start failing overnight**: zip RUSTSEC-2026-0367/0368/0369 appeared 2026-10-09/10. Check reachability (grep for the vulnerable API), then record an exception in `.cargo/audit.toml` with the reasoning and a review date, as for rsa.
- **`check_ts_bindings.sh` compares against the sibling `../unitprep-ui`**, so in a worktree it checks the wrong copy; pass the worktree's path explicitly (`./scripts/check_ts_bindings.sh ../unitprep-ui-pass2`). Likewise the UI preflight step 9 reads `../unitprep-api`.
- **Subagent hand-off for a big mechanical move works** when given its own worktree, its own `CARGO_TARGET_DIR`, an explicit "never touch the main checkout" rule and a before/after test-list comparison; still re-verify the cherry-pick yourself.
