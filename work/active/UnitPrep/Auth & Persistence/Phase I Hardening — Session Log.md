## 2026-07-31 16:47 — Shipped: fatal startup guardrail against SESSION_COOKIE_SECURE=false on a real deployment

Implemented the Phase I "HTTPS mandatory / SESSION_COOKIE_SECURE guardrail" item from the auth hardening plan. unitprep-api now refuses to start if SESSION_COOKIE_SECURE=false is paired with a non-localhost WEBAUTHN_RP_ORIGIN, closing the silent-misconfiguration risk the GitHub LLM review and the vault's own assessment both flagged.

**What changed**: `src/auth/session_cookie.rs` — added `is_localhost_origin` (private) and `validate_cookie_security` (pub), plus 4 unit tests. `src/auth/mod.rs` — re-exported `validate_cookie_security`. `src/main.rs` — calls `validate_cookie_security(&rp_origin)` right after `rp_origin` is resolved, panics with a clear message on failure, same pattern as the existing DB-pool and WebAuthn-backend fatal checks.

**Decisions**: Refuse-to-start (panic) rather than a startup warning, matching the codebase's existing fail-fast convention for fatal misconfiguration (DB pool, WebAuthn backend, sqlx migration checksums) rather than introducing a new class of "log and continue" at boot. Localhost detection is done by checking the origin's host against literal "localhost"/"127.0.0.1" rather than introducing a new APP_ENV/environment-tier concept — the codebase had no existing environment concept, and WEBAUTHN_RP_ORIGIN already had to be set correctly for any real deployment, so it was the cheapest existing signal to key off.

**Verification**: `cargo build` (0 warnings), `cargo clippy --bin unitprep -- -D warnings` (clean), `cargo fmt --check` (clean), `cargo test --bin unitprep` (229 passed, 0 failed — 225 pre-existing + 4 new for `validate_cookie_security`).

## 2026-08-03 15:51 — Completed Phase I item 1 — audit-event coverage verification, 3 gaps found and fixed

Did the closing audit-coverage pass (Phase I item 1 of the auth roadmap): read every auth handler (register, login, logout, TOTP, invites) end to end against the canonical event list in `audit_log.rs`, looking specifically for the same asymmetry shape that was fixed on 2026-07-30 (a rejection path that returns early with no audit row while a comparable path in the same or a sibling handler does log). Found and fixed three real gaps, all the same shape; confirmed several other candidate gaps were deliberate and left them alone.

**What changed**: `src/api/auth_login.rs` — `login_begin`'s empty/whitespace-email early return now writes `LOGIN_FAILED` (reason: `empty_email`) before returning, matching the very next case (email doesn't resolve to a credential) which already logged. `src/api/auth_totp.rs` — login's combined `email.is_empty() || !totp_configured()` early return was split into two checks, each now logging `LOGIN_FAILED` with a distinct reason (`empty_email` / `totp_not_configured`, both tagged `factor: totp`) before returning the same opaque response either way — the HTTP response stays identical (anti-enumeration is about what the caller sees, not what the audit row records). `src/auth/audit_log.rs` — added a new event constant, `INVITE_REFUSED`, for an admin's invite-issuance attempt against an ineligible existing account. `src/api/auth_invites.rs` — `Outcome::Refused` changed from a bare String to `{user_id, reason: &'static str, message: String}` so the two refusal branches (`already_credentialed`, `not_invited_status`) in `issue_invite` carry a structured reason; `create_invite`'s match arm now writes an `INVITE_REFUSED` audit row (`Subjects::by(admin).about(target_user_id)`) before returning the conflict response.

**Decisions**: Scoped the sweep to genuine asymmetries (a rejection unaudited while a comparable one in the same handler is), not exhaustive audit-everything. Explicitly left several candidate gaps alone as deliberate: `auth_logout`'s no-cookie case (documented in its own module doc as intentionally unaudited to avoid oracle-filling noise), `auth_invites`' structural validation failures (bad email/name/company format — an authenticated admin's own typo, not a probing signal), and the `AuthenticatedUser` extractor's ordinary session-expiry 401s (would fire on every unauthenticated page load once routes are gated in Phase I item 5 — auditing those would be pure noise, not a security event). Also left the "session verified but session-creation failed" branches in both `register_finish` and `login_finish` unaudited — a real successful crypto auth that never got a session is arguably audit-worthy, but it's a symmetric infra-failure case (DB down) present identically in both handlers already, not an asymmetry, so it was noted but not fixed in this pass. For the TOTP login split, deliberately logged a MORE specific reason (`totp_not_configured`) in the audit row than the HTTP response ever reveals (which stays the same opaque 401 either way) — anti-enumeration constrains the caller-visible response, not what an operator can see in their own audit log, and an operator genuinely benefits from telling "TOTP is off here" apart from "someone tried a bad address".

**Verification**: `cargo build --bin unitprep` (0 warnings), `cargo clippy --bin unitprep -- -D warnings` (clean), `cargo fmt --check` (clean), `cargo test --bin unitprep -- --test-threads=1` (225 passed, 0 failed). Note: default parallel `cargo test --bin unitprep` (no `--test-threads=1`) shows 2 unrelated pre-existing failures from a `TOTP_ENCRYPTION_KEY` env-var test-isolation race not touched by this change — confirmed pre-existing and spun off as a separate flagged task rather than fixed here, since it's orthogonal to audit coverage.

## 2026-08-03 16:10 — Fix TOTP_ENCRYPTION_KEY test-isolation race with serial_test

`src/api/auth_totp.rs` and `src/auth/totp.rs` both mutate the process-global `TOTP_ENCRYPTION_KEY` env var across their `#[test]`/`#[tokio::test]` functions with no serialization, causing intermittent failures under the default parallel `cargo test --bin unitprep` (confirmed: one thread's `set_var`/`remove_var` visible mid-assertion in another). Fixed by adding `serial_test` as a dev-dependency and tagging every env-touching test in both files with a shared `#[serial(totp_env)]` lock, rather than serializing the whole suite or refactoring the production code path.

**What changed**: `Cargo.toml` — added `serial_test = "4"` to `[dev-dependencies]` with a comment explaining why (shared named lock across two files touching the same global env var). `src/api/auth_totp.rs` — added `use serial_test::serial;` in `mod tests` and `#[serial(totp_env)]` on the 3 tests that `set_key()`/`remove_var("TOTP_ENCRYPTION_KEY")`. `src/auth/totp.rs` — added `use serial_test::serial;` in `mod tests` and `#[serial(totp_env)]` on the 8 tests that call `with_key()` or mutate `KEY_ENV` directly (left `matches_the_rfc_6238_test_vector` and `the_provisioning_uri_names_the_issuer_and_account` untagged since they never touch the env var).

**Decisions**: Chose `serial_test`'s named-lock approach (option a from the brief) over documenting `--test-threads=1` (option c) or refactoring production code to accept the key as a parameter (option b) — the brief flagged (b) as too invasive for already-reviewed auth code, and (a)/(c) were preferred. Used a single shared lock name `totp_env` across both files rather than per-file locks, because the race is cross-file: both files mutate the exact same global env var, so serializing only within one file would not have fixed it. Did not touch `src/auth/session_cookie.rs` even though it has the identical bug pattern (`SESSION_COOKIE_SECURE` mutated by multiple `#[test]`s, confirmed to flake once in 10 parallel runs) — out of scope for this task, flagged separately as a spawn_task suggestion instead of fixing inline.

**Learned**: The race was broader than the two tests named in the original bug report — it actually spans two files (`src/api/auth_totp.rs`'s 3 tests and `src/auth/totp.rs`'s 8 tests), all sharing one process-global env var. Grepping the whole repo for the env var name before scoping the fix was necessary to catch this. The same env-var-mutation-without-serialization pattern exists at least one more place in this codebase (`src/auth/session_cookie.rs`, `SESSION_COOKIE_SECURE`) — worth a repo-wide grep for `std::env::set_var`/`remove_var` in test modules next time this class of bug comes up, rather than assuming it's contained to one file.

**Verification**: `cargo build --bin unitprep --tests` succeeded. `cargo test --bin unitprep -- --test-threads=1` passed 225/225. `cargo test --bin unitprep` (default parallel) run 10 consecutive times with zero failures (225 passed each time) after the fix — prior to the fix this was confirmed flaky. One of those 10 runs did surface the separate, pre-existing `session_cookie.rs` flake (224 passed/1 failed, unrelated to this fix), which was flagged as a follow-up task rather than fixed here.

## 2026-08-03 16:50 — Completed Phase I item 2 — rate limiting on unauthenticated auth endpoints + invite creation

Added real rate limiting (Phase I item 2 of the auth roadmap) using `tower_governor` (a Tower/Axum middleware over the `governor` crate's in-process token-bucket limiter) — no hosted/edge rate-limiting service, consistent with the project's self-hosted-library-over-service preference. One shared bucket covers every unauthenticated auth endpoint (passkey register begin/finish, passkey login begin/finish, TOTP login); a separate, more generous bucket covers authenticated invite creation.

**What changed**: `Cargo.toml` — added `tower_governor` 0.8, default-features off (drops the unused tonic/gRPC feature), axum + tracing features only. `src/api/mod.rs` — built two `GovernorConfig` instances (auth: burst 10, refill 1/3s ≈ 20/min sustained; invites: burst 20, refill 1/2s), split the 6 affected routes into their own `auth_routes`/`invite_routes` sub-routers merged back into the main chain before `.with_state` (merge requires matching `Router<S>` state types), spawned one background tokio task calling `retain_recent()` on both limiters every 60s (mirrors `InMemorySessionStore::start_cleanup_task`'s shape) to stop the keyed `DashMap` growing unboundedly, and added a `rate_limit_exceeded` error handler mapping `tower_governor`'s default plain-text 429 onto this project's `{error, message}` `ApiErrorBody` shape (same motivation as the existing `normalize_extraction_rejection_body` middleware). `src/main.rs` — `axum::serve` now uses `into_make_service_with_connect_info::<SocketAddr>()` instead of `into_make_service()` — required for `tower_governor`'s default `PeerIpKeyExtractor` to have anything to key on. `src/api/http_integration_tests.rs` — `spawn_test_server` updated to match (`into_make_service_with_connect_info`), plus two new real-HTTP tests: one drives 11 requests at `/auth/login/begin` and asserts the 11th (only) is 429 with the standard error shape, the other exhausts the auth bucket then confirms `/auth/invites` is unaffected (a 401 from the auth extractor, not a 429), proving the two buckets are actually independent rather than accidentally generous enough to look independent.

**Decisions**: Keyed by peer IP via `tower_governor`'s default `PeerIpKeyExtractor` (requires `ConnectInfo<SocketAddr>`), NOT by any client-supplied header (`X-Forwarded-For` etc.) — deliberately the same unresolved-trust-boundary question as the `ip_address` NULL already documented in `auth_register.rs`/`auth_login.rs` (no trusted-reverse-proxy policy exists yet since hosting is undecided). Documented that behind a proxy that doesn't preserve the real TCP peer, this degrades to one shared bucket for everyone behind that proxy — strictly more restrictive than intended, never less, so safe to ship now and revisit once hosting/proxy trust is decided (same trigger as the IP-capture question). One shared bucket across all 5 unauthenticated auth endpoints (register begin/finish, login begin/finish, totp login) rather than one bucket per route — deliberate, so a script can't multiply its effective budget by spreading attempts across endpoints instead of hammering one. Invite creation given its own separate, more generous bucket rather than joining the anonymous-endpoint bucket, since it's authenticated/admin-only already and the concern is accidental/scripted hammering by a trusted caller, not anonymous probing — explicitly verified independent with a real test rather than assumed. Added a custom `error_handler` to normalize `tower_governor`'s default plain-text 429 body to the project's standard `{error, message}` JSON shape, reusing the exact reasoning already established for `normalize_extraction_rejection_body` — decided this was cheap enough (one small function) to do now rather than let a third inconsistent error shape exist until the frontend is built.

**Verification**: `cargo build` (0 warnings), `cargo clippy --bin unitprep -- -D warnings` (clean), `cargo fmt --check` (clean), `cargo test --bin unitprep -- --test-threads=1` (227 passed, 0 failed — 225 prior + 2 new). The 2 new tests specifically exercise the real HTTP stack (not just config construction) and would fail if `ConnectInfo` wiring, the burst-size math, or the bucket-independence were wrong.

## 2026-08-03 17:38 — Completed Phase I item 3 — admin-mediated account recovery (revoke-and-reissue)

Extended invite issuance to support account recovery: an admin can now revoke every existing access path on an already-active, credentialed account and issue a fresh invite, closing the gap where re-issuing an invite was unconditionally refused for any account that already held a credential. This is the piece that makes the admin-mediated recovery workflow described in `AUTHENTICATION.md` actually possible, not just described.

**What changed**: `migrations/20260803120000_add_set_user_status_for_recovery.{up,down}.sql` — new `auth.set_user_status(user_id, status)` `SECURITY DEFINER` function: the first one whose safety depends on checking the caller's role via the `app.current_user_role` GUC rather than being scoped by a token or the caller's own `user_id`. Returns `BOOLEAN` (whether a row was actually updated) rather than `VOID`, needed because a bare `SELECT function()` always reports one row back regardless of what happened inside the function body. Deliberately generic (not recovery-specific) so a future admin feature needing a status change reuses this rather than writing its own copy of the same admin check. `src/auth/audit_log.rs` — added `ACCOUNT_RECOVERY_INITIATED` event, kept distinct from `INVITE_CREATED` since recovery is materially more consequential (destroys existing credentials, not just adds a path for someone who never had one). `src/api/auth_invites.rs` — new `POST /auth/invites/recover` endpoint (`recover_account` handler) and `RecoverAccountRequest`/`RecoveryOutcome` types. Looks up the account by email, requires `status='active'` (refuses `invited` with reason `not_yet_enrolled` — use the regular invite endpoint instead — and `deactivated` with reason `account_deactivated` — reactivation is a separate decision), then cycles status through `deactivated` and back to `invited` inside one transaction so the EXISTING revoke-all-access-paths trigger (`migrations/20260730*_*.sql`) does the work of wiping passkeys, TOTP, live sessions, and any outstanding invite, rather than duplicating those `DELETE`s in new code. Checks the first `set_user_status` call's boolean return before proceeding, refusing with reason `account_changed_concurrently` if the account stopped being recoverable between the initial `SELECT` and the status flip (both inside the same transaction, so only a genuinely concurrent actor could cause this). `src/api/mod.rs` — wired `/auth/invites/recover` into the same `invite_routes` sub-router as `/auth/invites`, sharing its rate-limit bucket (same trust level: authenticated admin). `src/api/auth_invites.rs` tests — added input-validation coverage for the new endpoint matching the existing `create_invite` test style.

**Decisions**: Separate endpoint (`POST /auth/invites/recover`) rather than a recovery flag on `create_invite` — the two operations have very different blast radii if triggered by accident (recovery destroys existing credentials), and a separate route makes the admin's intent unambiguous at the point of the request rather than resting on a boolean default. Reused the existing deactivation trigger by cycling status through `deactivated` rather than writing new `DELETE` statements for `webauthn_credentials`/`totp_credentials`/`sessions`/`user_invites` — directly follows the precedent those migrations' own comments set ("a guarantee living in application code holds only for the code paths that remember it... a trigger holds for all of them"). Writing a second copy would have been exactly the mistake those migrations warn against. `set_user_status` is a generic admin primitive, not recovery-specific, on the theory that the next admin feature needing a status change (deactivating a user, say) should reuse it rather than each admin action inventing its own copy of the same admin-role check and `UPDATE`. Did not attempt to distinguish "not found" from "wrong status" via the SQL function's return value — instead did the existence+status lookup as a plain `SELECT` in Rust (same RLS-permitted pattern `issue_invite` already uses) and only ever call the privileged `SECURITY DEFINER` function once eligibility is already confirmed within the same transaction.

**Verification**: Migration applied to the dev branch via `sqlx migrate run` and manually verified twice against the real schema in rolled-back transactions (never committed): (1) confirmed `set_user_status` raises when no admin GUC is set, correctly flips status when one is, and its boolean return value correctly distinguishes a real update from a no-op against a nonexistent row; (2) confirmed the full recovery sequence end-to-end against a real existing account — a pre-existing live invite was retired by the trigger, `webauthn_credentials` dropped to zero, status ended at `invited`, and exactly one live invite (the fresh one) remained afterward. Rust side: `cargo build`/`clippy -D warnings`/`fmt --check` all clean, `cargo test --bin unitprep -- --test-threads=1` 229 passed (225 prior + 2 new + 2 from the rate-limiting work already counted), confirmed stable under repeated default parallel `cargo test` runs too.
