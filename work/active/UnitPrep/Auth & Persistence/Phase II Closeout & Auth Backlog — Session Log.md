## 2026-08-04 21:31 — step_up_actions wired up, mandatory_passkey_enrollment dropped, TOTP disable removed and re-enrollment gap closed

Followed up on the `auth_configuration`/TOTP-disable discussion: wired `auth.auth_configuration.step_up_actions` into a real, generic step-up-policy check (replacing a hardcoded hardcode for "add a passkey"); dropped the vestigial `mandatory_passkey_enrollment` column; removed the TOTP disable action end-to-end (backend endpoint, frontend button) since it had a self-lockout risk with no security upside; and closed a real gap in TOTP re-enrollment where the old factor stopped working the moment `/enroll/begin` was called, not when the new one was actually confirmed. Backend rebuilt and restarted with the new binary. All uncommitted, verified by compile + full test suites both repos + direct SQL verification against the real dev branch.

**What changed**: `migrations/20260804150000_step_up_policy_and_totp_reenroll.{up,down}.sql` — drops `auth_configuration.mandatory_passkey_enrollment`; seeds `step_up_actions` with `['add_passkey']` so wiring it up doesn't silently disable existing protection; adds a second RLS SELECT policy (`auth_configuration_select_any_authenticated`) so a non-admin caller can read policy for their own action, while writes stay admin-only; adds `auth.totp_credentials.pending_secret_encrypted` and drops `secret_encrypted`'s NOT NULL (a brand-new enrolment can now exist with nothing confirmed yet). `src/auth/step_up_policy.rs` (new) — `action_requires_step_up(db, user_id, action)` reads `auth_configuration.step_up_actions` under the caller's own owner-scoped RLS transaction using the JSONB `?` containment operator; `ADD_PASSKEY` constant. `src/api/auth_register.rs` — the passkey-add step-up gate (previously an unconditional `user.is_elevated()` check) now first asks `action_requires_step_up(ADD_PASSKEY)` and only enforces elevation if the policy says so. `src/api/auth_totp.rs` — `store_unconfirmed_secret` writes only to `pending_secret_encrypted` now, leaving an existing confirmed secret/`confirmed_at`/lockout state completely untouched; `confirm_own_secret` promotes `pending_secret_encrypted` into `secret_encrypted` (clearing pending) only on a verified code; `load_own_secret` reads `pending_secret_encrypted` instead of `secret_encrypted`; `disable()` handler and `delete_own_secret()` deleted entirely. `src/api/mod.rs` — `POST /auth/totp/disable` route removed. `src/auth/audit_log.rs` — `TOTP_REMOVED` event constant removed (its only writer was `disable()`). `src/auth/authenticated_user.rs` — separately, the `.map_err(|_| internal_error())` silent-error-swallow bug found earlier this session (while debugging the "Failed to verify session" report) is fixed here too, still uncommitted. unitprep-ui `app/(app)/account/page.tsx` — "Remove authenticator app" + confirm-disable flow deleted; "Update authenticator app" now reveals the same `TotpEnrollForm` (already generic enough to serve first-enrolment and re-enrolment identically) with a Cancel option; `lib/auth.ts`'s `totpDisable()` removed. `AUTHENTICATION.md`, `THREAT_MODEL.md`, `CHANGELOG.md` updated for all of the above; `THREAT_MODEL.md`'s known-gaps section also pre-flagged the rate-limit-logging and session-expiry-audit gaps about to be built next.

**Decisions**: `step_up_actions` read via a new RLS SELECT policy open to any authenticated caller, not a `SECURITY DEFINER` bypass function — `auth_configuration` was previously admin-only-readable, and since policy content (which actions need step-up) isn't sensitive to a signed-in user, widening SELECT (while leaving writes admin-only) was simpler than adding a new bypass function for this one read. `secret_encrypted` made nullable rather than keeping two different code paths for first-enrolment vs re-enrolment — a brand-new `totp_credentials` row can now legitimately have no live secret yet (only a pending one), which lets `store_unconfirmed_secret`/`confirm_own_secret` be the same two statements regardless of whether this is someone's first TOTP factor or their fifth re-enrolment. Verified safe: the only reader of `secret_encrypted` for step-up purposes already filters `confirmed_at IS NOT NULL`, and `confirmed_at` is only ever set in the same statement that populates `secret_encrypted`. TOTP disable removed entirely (backend + frontend), not just hidden in the UI — Boris explicitly deferred the call to Claude's judgment ("unless you don't feel it's a good idea"); reasoning was attack-surface/dead-code hygiene (an endpoint nothing calls is one more thing sitting in the threat model), not a security requirement, since the capability was already self-scoped to the caller's own account.

**Verification**: `cargo check --all-targets` clean; migration applied to the real Neon dev branch; the pending-secret promotion logic verified directly in a rollback transaction (old secret stays live through "begin", pending holds the candidate, promotion on "confirm" correctly swaps `secret_encrypted` and clears pending, first-time enrolment correctly allows NULL `secret_encrypted`); the new RLS policy verified by connecting as the real `app_service` role (not `SET ROLE` from owner, which is documented elsewhere as failing) — no identity GUC set returns 0 rows, a non-admin `app.current_user_id` returns 1 row with `add_passkey` correctly present in `step_up_actions`. Frontend: `tsc --noEmit` clean, 287/287 vitest tests passing. Backend rebuilt (`cargo build --release`) and the running server process restarted on the new binary, confirmed via `/health/db`.

**Open**: Changes uncommitted on disk in both repos — still pending review/commit, along with the earlier logout-redirect fix, dedup double-fetch fix, and the session-verification logging fix from earlier today. Still queued and approved but not yet built: a `session_expired_access_attempt` audit event, rate-limit-rejection audit logging, a new "Onboarding Manager" role, and the disable-user admin action (queued for after Phase II close-out). `auth_configuration.allowed_factors` intentionally left untouched — flagged for revisit once a hardware-bound-passkey decision is made, since its current flat-array shape may not survive a role-scoped requirement.

new routes registered. `THREAT_MODEL.md`, `CHANGELOG.md` — Known gaps section updated (3 gaps closed, 1 new schema-only-role gap added); Unreleased section documents the six items. unitprep-ui `lib/auth.ts` — added `Role` type union, `disableUser()`, `listAuditLogs()` with `AuditLogFilters`/`AuditLogEntry` types; **Decisions**: Kept `onboarding_manager` strictly schema-only per the approved item's own wording ("approved, not yet added to the Role enum/schema") — no invite-creation path can assign it, every admin-gated match treats it as authenticated-but-refused. Deliberately did not invent a permission surface for it, since which roles may do what is an explicit open decision logged elsewhere in the vault, not this task. Did NOT build the full Security tabbed page (Authentication Policy/Users/Groups/Audit Logs tabs) from `Architecture.md`'s original vision doc — that's speculative future scope beyond what was actually approved. Added Audit Logs as its own top-level nav entry instead, alongside the existing flat Users route, matching the smaller actual ask. `ip_address` wiring is intentionally partial, not universal: added `ConnectInfo` to handlers that were cheap to extend (`create_invite`, `recover_account`, `deactivate_user`, the new authorization-failure arms) and to the two already-had-it login/register success paths; left `login_begin`/`register_begin`/TOTP handlers at `None` rather than retrofitting `ConnectInfo` everywhere, since those either predate identity resolution or have no natural IP source in scope without disproportionate churn. `rate_limit_rejected` carries no `ip_address` — `tower_governor` 0.8's `error_handler` receives only the `GovernorError`, not the original request/`ConnectInfo`, so getting the IP there would need a custom middleware wrapper rather than the error_handler hook; judged not worth it for this pass. `before_state`/`after_state` populated for exactly the schema's own named diff-worthy events (`user_deactivated`, `account_recovery_initiated`) rather than retrofitting it onto every status-adjacent event. Chose `Change::from_to`/`Change::none()` as a small `Subjects`-style named struct instead of two bare `Option<Value>` parameters, specifically to avoid the same before/after transposition risk `Subjects` was originally built to prevent.

**Learned**: The live unitprep-api process the user already had running on :8080 (release build, started hours earlier) predates all of this session's changes — hitting the new `/auth/audit-logs` route against it returns 404, not a bug, just stale code. Spun up an isolated instance on :8091 instead to verify end-to-end (confirmed a real `rate_limit_rejected` row landing in the actual dev database with the new columns), then stopped it and left the user's live server and its in-memory session state untouched rather than restarting it. Accidentally collided with the user's own `/tmp/unitprep-api.log`: my first backgrounded verification attempt used the same conventional path their long-running server apparently already writes to, and a `>` redirect truncates the underlying inode even for a process with an already-open fd to it — so my truncation attempt landed on their live process's own log, not a fresh file. Harmless (ephemeral tracing output, not the audit table), but worth remembering: pick a path that can't collide with a possibly-already-running instance (e.g. a PID- or port-suffixed name) before backgrounding anything in a repo that might already have a dev server up. A one-off `wsl.exe -e bash -lc "... &"` background launch does not reliably survive past that single tool invocation returning (`nohup`/`disown`/`setsid` did not save it) — the Bash tool's own `run_in_background: true` on the `wsl.exe -e bash -lc "cargo run"` command was what actually persisted a long-running WSL process across separate tool calls.

## 2026-08-04 22:46 — Added role selection: invite-time role picker + standalone role-change action

Resolved the open "which roles may an admin grant" question from the disable-user/audit-log session: any admin may now assign either role (admin or `onboarding_manager`) when creating an invite, and change an already-enrolled user's role via a new standalone endpoint. Both surfaced as dropdowns in unitprep-ui (invite form + a per-row select on the admin Users table).

**What changed**: unitprep-api `migrations/20260804180000_add_set_user_role.{up,down}.sql` — new `auth.set_user_role(user_id, role)` `SECURITY DEFINER` function, admin-only, mirroring `auth.set_user_status` exactly (`role` has no direct `UPDATE` grant per `restrict_users_update_columns`). unitprep-api `src/auth/audit_log.rs` — added `ROLE_CHANGED` event constant. unitprep-api `src/auth/authenticated_user.rs` — `Role::from_db_text` made `pub` (now the shared parser for request-body role strings, not just DB text). unitprep-api `src/api/auth_invites.rs` — `CreateInviteRequest` gained a required `role: String` field, validated via `Role::from_db_text` before any query runs; `IssueInvite` struct threads `role` into the new-user INSERT (direct bind, INSERT has no column-level grant restriction) and, on reissue, into a `SELECT auth.set_user_role(...)` call (the existing-row branch is an UPDATE, which IS column-restricted); `INVITE_CREATED` audit metadata now carries the assigned role. unitprep-api `src/api/auth_user_role.rs` (new) — `POST /auth/users/{id}/role`, admin-gated (403 + `authorization_failure` for `onboarding_manager`), refuses changing one's own role, refuses a no-op/already-that-role change, audits `role_changed` with a real before/after diff via `auth.set_user_role`. unitprep-api `src/api/mod.rs` — registered the new route. unitprep-api `THREAT_MODEL.md`, `CHANGELOG.md` — updated the `onboarding_manager` gap note (assignment is no longer missing) and documented the new endpoints. unitprep-ui `lib/auth.ts` — `CreateInviteRequest.role: Role` (required); new `VALID_ROLES: {value,label}[]` display list; new `changeUserRole(userId, role)`. unitprep-ui `app/(app)/admin/users/page.tsx` — Role select added to the invite-creation form (3-column grid with Company/Job title); new Role column with a per-row select calling `changeUserRole` on change, disabled for self and while any row action is pending; reissue re-sends the user's current role unchanged.

**Decisions**: Any admin may assign either role to anyone — no further restriction (e.g. "only admins can grant admin") was added, since there is still only one real distinction (admin vs. everything-else-gets-403) and `onboarding_manager` has no permissions of its own yet to make a finer allowlist meaningful. Role changes on an existing user go through a dedicated `SECURITY DEFINER` function (`auth.set_user_role`) rather than a direct UPDATE, matching `set_user_status`'s precedent exactly — role has no application-facing UPDATE grant at all (`restrict_users_update_columns` names it explicitly as the escalation vector that migration exists for), so a direct UPDATE from the invite-reissue RLS transaction would have failed at runtime; caught this via review before it shipped as a real bug (the initial draft used a raw UPDATE for the reissue path). Reissuing an invite re-applies whatever role is in the request, not just the original invite's role — treated as a feature (fixing a wrong role assignment before the user ever enrolls) rather than an inconsistency to avoid, since the account has no session/established behavior yet at that point. The role-change endpoint refuses a caller changing their own role (mirrors `deactivate_user`'s self-refusal) — a structural guard against an admin locking themselves out, rather than relying on a frontend confirm dialog. Kept the row-level role dropdown as a plain `<select>` with no separate confirm step, per the user's literal ask ("a dropdown in the user row") — unlike disable/recover, which have an explicit two-click confirm.

**Learned**: Column-level UPDATE grants (set up in `restrict_users_update_columns` for exactly this reason) will silently doom a direct SQL UPDATE on a restricted column at runtime with a permission-denied error that `cargo test`'s lazy-pool tests cannot catch — worth grepping for "role" or "status" in any new direct `auth.users` UPDATE before assuming it'll work, rather than only checking it against RLS.

**Verification**: `cargo check` clean, full test suite 248/248 passing (3 new tests: invalid-role rejection, `onboarding_manager`-accepted-as-a-role, plus 3 new tests in `auth_user_role.rs` covering forbidden-role/invalid-role/self-refusal). Migration applied cleanly to the Neon dev branch. Frontend: `tsc --noEmit` clean, eslint clean, vitest 287/287 passing. Live-verified via an isolated instance on a spare port (separate from the already-running dev server): `POST /auth/users/{uuid}/role` correctly 401s unauthenticated; confirmed `auth.set_user_role` exists as a real `SECURITY DEFINER` function via direct psql query. Browser-verified the updated Users page against the real running unitprep-ui dev server via HMR — new bundle compiles with no console errors.

**Open**: `onboarding_manager` still has no permissions of its own — every admin-gated action refuses it. Assigning the role is solved; what it should be allowed to do is still the open design question. No "last remaining admin" guard — the self-role-change refusal prevents locking yourself out directly, but nothing stops two admins from each demoting the other down to zero real admins left. Not addressed this pass; flag if it ever becomes a real scenario with more than one admin. (Note: a last-remaining-admin guard was in fact built the next day, 2026-08-05, in work outside this satellite's scope.)
