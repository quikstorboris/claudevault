## 2026-08-03 23:03 — TOTP repurposed from login-fallback to step-up-only, and proxy.ts route gating shipped — Phase I frontend build is now complete

Boris flagged that TOTP being usable as a full login factor conflicted with his intent (step-up verification for sensitive actions only, not a second way to sign in) — confirmed against the vault this was a real, deliberate prior decision (Phase 2 task 9, 2026-07-30), not a misremembering, but agreed the redesign was right: admin-driven account recovery (shipped 2026-08-03, same day) now covers the "lost your only passkey" gap TOTP-as-login used to plug, so keeping a static shared secret as an equally-capable full login path next to a hardware passkey was undercutting the account's real security floor for no remaining benefit. Removed TOTP-as-login entirely, added session step-up elevation, forced TOTP enrolment into onboarding, and then shipped `proxy.ts` route gating — the last item on the original Phase I/frontend roadmap. Boris stepped away mid-session ("proceed to step 8... I will test all the TOTP changes tomorrow"), so this was carried to completion autonomously and left in a fully green, curl-and-vitest-verified state for him to pick up.

**What changed**: unitprep-api `migrations/20260803150000_totp_step_up_not_login.{up,down}.sql` (new) — added `auth.sessions.elevated_until`; `resolve_session()` now also returns it (required `DROP`+`CREATE`, not `ALTER`, since its `RETURNS TABLE` column list changed); new `auth.record_step_up(token_hash, minutes)` `SECURITY DEFINER` function, self-scoped by `token_hash` the same way `resolve_session` is (no admin check needed). unitprep-api `src/auth/authenticated_user.rs` — `AuthenticatedUser` gained `token_hash` and `elevated_until` fields plus `is_elevated()`; copy changed throughout from "backup way to sign in" to "confirm sensitive actions like replacing a passkey". unitprep-ui `proxy.ts` (new) — Next.js 16 route gating: redirects to `/login` when the `unitprep_session` cookie is entirely absent, for every path except `/login` and `/invites/*`; deliberately does not verify the cookie is a real/valid session (that stays server-side, per request, where it already happens correctly) — see the dedicated vault memory on `proxy.ts`'s export-name requirement, which cost real time to reverse-engineer from Next's own compiled source.

**Decisions**: Removed TOTP login rather than leaving it reachable-but-discouraged — an endpoint that still works is a live security surface regardless of whether the UI still points at it; deleting `/auth/login/totp` outright was the only way to make "TOTP cannot log you in" actually true rather than merely UI-enforced. Elevation lives on the session row (`auth.sessions.elevated_until`), not the user row — step-up must be per-device: proving a code on one browser session must not silently elevate every other session the same user has open elsewhere. 5-minute step-up window, mandatory (unskippable) onboarding enrolment, and step-up gating scoped to just "add/replace a passkey" for this first pass — all three per Boris's explicit answers when asked; "API credentials" gating was named as a future sensitive action but has no endpoint yet, so nothing was built for it beyond the general step-up primitive being ready to reuse. Deleted the `ElevatedUser` extractor after writing it, once `register_begin`'s real shape (must serve both an elevated-session caller AND an unauthenticated invite-token caller from one handler) turned out to need an inline `is_elevated()` check instead — left as a lesson: design the gating primitive against the actual calling shape before generalizing it into an extractor. `proxy.ts` checks cookie PRESENCE only, not validity, and does not also enforce the mandatory-TOTP-onboarding redirect — that stays a client-side check in the `(app)` layout, specifically to avoid an edge-runtime fetch to the separate backend origin on every single navigation for a check the app already makes correctly downstream.

**Learned**: `auth.webauthn_credentials`' RLS policy has NO admin-bypass clause (unlike `auth.users`/`auth.totp_credentials`) — querying it as admin without also setting `app.current_user_id` to the specific row's owner returns zero rows for everyone, which looks exactly like "nobody has any credentials" and cost a few minutes of false alarm before re-reading the policy definition. Next.js 16's `proxy.ts` entrypoint template resolves the handler as `(isProxy ? mod.proxy : mod.middleware) || mod.default` — naming the exported function `middleware` inside a file named `proxy.ts` silently produces no working handler at all (falls through to an undefined default and throws `ProxyMissingExportError`). Recorded as its own general vault memory since this isn't spelled out clearly in the public migration docs and is an easy mistake given how much existing knowledge says "export function middleware". The entire step-up mechanism (enroll → confirm → step-up → `register_begin` gate) was verified end-to-end against the real dev database and real running binary purely via curl and a hand-rolled ~20-line stdlib-only Python TOTP generator — no browser, no real authenticator app, no WebAuthn ceremony needed, since none of TOTP's own mechanics require one. Minting a real session directly via the sanctioned `auth.create_session()` `SECURITY DEFINER` function (rather than a raw INSERT, which RLS correctly refused) made this fully legitimate rather than a bypass.

**Decisions**: Asked which item "phase 9" meant rather than guessing — item 8 (build a UI feature) and item 9 (verify an existing capability) are different enough in shape that picking wrong would have meant real wasted work. Boris chose item 8. `list_users` lives in its own new file (`auth_users.rs`), not folded into `auth_invites.rs` — listing (a read) is a different concern from invite/recovery (writes), matching the standing "split mixed-concern files" preference. The listing needed a new `SECURITY DEFINER` function rather than a plain admin-scoped query, because of a gotcha already recorded once this session: `auth.webauthn_credentials`' RLS policy has no admin-bypass clause, so a naive join would silently show every other user's `credential_count` as zero. Chose to fold each repo's dependency-manifest/version-bump changes into their own dedicated "Bump version to X" commit ONLY when nothing else in that push needed the manifest change simultaneously (true for the Users-tab round, no new dependency); the prior round's `qrcode` addition had to travel with its own feature commit instead, since separating it would have left an intermediate commit whose code imports a dependency its own manifest didn't have yet.

**Learned**: The exact same `webauthn_credentials`-RLS-has-no-admin-bypass gotcha bit twice in one work session (once debugging "why does credential count read as zero", once here while designing a new query from scratch) — worth remembering as a standing fact about this schema specifically, not just a one-off debugging war story. Full end-to-end browser verification of an authenticated admin page is possible without a real WebAuthn ceremony: mint a real session server-side via `auth.create_session`, then inject the raw token into the browser via `document.cookie = "name=value"` from the automated browser's own JS context. This works because `HttpOnly` only blocks *reading* an existing cookie of that name via script — creating a fresh one when none currently exists is generally permitted, and since cookies are host-scoped (not port-scoped), the browser correctly sends it to both the Next.js origin (port 3000, for `proxy.ts`) and the separate API origin (port 8080, for the actual fetch calls) since both are "localhost". This is what actually caught the self-recovery bug — a curl-only verification pass would have missed it entirely, since curl has no notion of "the row representing the caller's own identity" the way a real rendered page does. The self-recovery bug itself is a generalizable UI pattern worth naming: any admin action that can target "any user including yourself," where the action revokes the *caller's own* access as a side effect when self-targeted, needs an explicit self-exclusion in the UI — not just at the API layer, since the API correctly performing the action IS the bug from the caller's point of view.
