# Questions and answers, 2026-10-16 (Part 1)

Part of [[Server Logging and Grafana - Index]]. What was *done* is in [[Build Timeline 2026-10-16 (Part 1)]]. Answers marked **(recalled, unverified)** came from memory, not from checking current docs or the code.

**1. Do we store server (Rust) logs today? If not, can we? A rolling week? Good idea?**
No: `src/startup/logging.rs` printed text to stdout; nothing stored. A week is a good idea (diagnose a report a day or two later; a week covers a weekend plus lag). Advice at the time: keep stdout, make it JSON, let the platform keep 7 days (Docker `json-file` limits in dev, journald/cloud in prod) instead of app-written files. Risks to handle: debug-level lines may carry tenant names or file contents (retain `info` only), text is hard to search (use JSON), check volume before committing to a size. Later found that the server is started via `docker compose exec`, which Docker does not capture, so the build used a file instead (see [[Server Logging Design and Decisions]]).

**2. "So you're saying local files for local dev and nothing in the DB?"**
Not exactly: the app writes no files in the stdout design; the platform stores the output. Nothing in the DB, and Claude recommended against it (volume, backup bloat, depends on the DB being up when the DB is what is broken). The business-level record already lives in the audit tables. Boris then decided: no DB, local files are fine on a schedule, Docker restrictions fine, JSON.

**3. An admin tool to process the JSON files, maybe with assistants and solution recommendations: silly or valuable?**
Two different ideas. A **log viewer** (search/filter) is worth it when needed and reuses the existing `useInfiniteLogFeed` pattern; a separate tool (Grafana/Loki, `lnav`, `jq`) needs no app code. **AI recommendations** from logs alone are weak (symptoms, not causes), and sending raw lines to an LLM sends tenant data to a third party. Suggested order: JSON + request IDs first; then point Claude Code at the log directory when something breaks; revisit an in-app viewer after living with the files.

**4. "I'm not worried about personal information in the log... Why would there be a need for any permissions? We're essentially manually selecting a file from any location on disk."**
Right if the viewer is a browser page that parses a file you pick: the server never touches it, so no server permission. Permissions matter only if the API reads its own log directory and serves it over HTTP. Redaction by recognising names is best effort (misses misspellings, company names used as people).

**5. "I linked a new Grafana account to my GitHub. What else can I do now?"** and **"assume I know nothing about Grafana, start from the beginning"**
Explained the four pieces (app -> Alloy courier -> Loki cabinet -> Grafana reading room), that Grafana Cloud hosts Loki and Grafana, and the plan: JSON logging, get Loki URL/user/token, Alloy in compose, Explore, later dashboards and alerts. Free-tier numbers were given from memory (recalled, unverified).

**6. "Where do I get the token?" / "Am I on the right page?" / "Look at this page and tell me what to do"**
Walked the portal (stack page -> Loki card -> Details), then the Access Policies page. The pasted token was an autogenerated **read** policy token (`hl-read`), the wrong kind for Alloy (needs `logs:write`) and now exposed in chat. Delete it; create a new policy with only `logs:write`, add a token with an expiry, paste it straight into `.env.local`, never into chat. Boris: token security is not a concern for him at this point; the new token was added.

**7. "So hold on, our logs won't be real time in Grafana?"**
They will: Alloy follows the file like `tail -f` and pushes in small batches; the file is only the hand-off. Measured: 10-100 ms in the tests.

**8. "Is this ready to be transferred to a live cloud environment (e.g. Fly.io), or only designed to work locally in Docker?"**
Half ready. Carries over: JSON format, `request_id`, `level`, `LOG_FORMAT=json` stdout. Dev only: the `alloy` compose service, the `LOG_DIR` files (cloud disks are ephemeral), the hardcoded `env=dev`/URL/user in the Alloy config. For Fly: stdout JSON, ship with `fly-log-shipper` (a separate app with a Loki output) or Alloy as a second process, credentials as host secrets, `env=prod` label, Grafana-side retention **(Fly specifics recalled, unverified)**. Boris then said: note everything about Fly.io; there is no prod today; he is the solo developer/tester/user; three live systems are connected; Neon has two environments with only dev in use; design forward-looking, "possibly but not necessarily fly.io". Recorded in [[UnitPrep Fly.io and Deployment Notes]].

**9. "Why would there be a need for any permissions?" follow-ups and "what do you think of the admin tool with AI?"**: see 3 and 4.

**10. What exactly is supposed to happen when my logs error? Is that a panic? How should it be handled?**
An `ERROR` log line is a **handled** error: the app logged it, returned an HTTP 500 and kept running; that is the app working as designed when the DB fails. A **panic** is an unexpected crash of a thread; `CatchPanicLayer` turns a handler panic into a 500 and the panic hook logs `panicked`. The original panic alert would not have caught the DB errors; an ERROR alert would have. Recommended adding an ERROR-count alert (noisy at first, tune after a week); Boris agreed.

**11. "Why are you asking for an email" / what other free Grafana features should I explore?**
Explore (ad-hoc queries, Live tail), Drilldown > Logs (point and click), Alerting, Dashboards; metrics/traces exist on the free tier but the app emits neither. Optional later: slow-route alert, a no-logs alert (to catch a dead shipper), metrics/traces.

**12. "Per-route latency: worth adding to the dashboard?" and "Do any other event groups deserve special attention (PS, Dropbox, ClickUp, anything else)?"**
Per-route latency times each endpoint separately (e.g. login 1 ms vs `/health/db` 433 ms); yes, added: slowest routes, p95 by route, 5xx by route, with ids collapsed so `/clients/<id>` is one route. Other groups: Process Street (calls by status, 429 waits, failures), Dropbox (success vs errors), DB connection errors, errors by module, slow SQL, ClickUp (**logged nothing at all**, hence the follow-up session), failed logins (only in DB audit tables, not logs).

**13. "Can you see server logs in Grafana any time I ask you?" / "Does Grafana have a CLI or SDK?"**
Two ways then: the JSON files (always, from WSL) and Grafana through Boris's Chrome session while a conversation runs (not unattended). Offered and then built: `logcli`, the Loki HTTP API, and `mcp-grafana`, all read-only with read tokens; also the Grafana HTTP API, `grafanactl`, the Terraform provider and the Foundation SDK **(recalled, unverified)**. Details: [[Reading Logs - Tools and Recipes]].

**14. "Remind me how to create proper tokens."**
Token 1 `GRAFANA_LOGS_READ_TOKEN`: portal -> Security -> Access Policies -> New access policy, realm the stack, scope **logs: Read** only, add a token with an expiry. Token 2 `GRAFANA_SERVICE_ACCOUNT_TOKEN`: in the stack, Administration -> Users and access -> Service accounts, role **Viewer**, add a token (`glsa_...`). Paste each as a plain `NAME=value` line in `.env.local`; verify with `grep -c`; never paste into chat.

**16. "What's next for Grafana? Is Sentry the same thing?"**
Next: restart the server, watch a week, check free-tier limits before 2026-10-30, make the alert email an admin setting, `env=prod` at the cloud move. **Sentry is not the same**: Sentry answers "what is crashing, how often, who is affected" (errors and panics grouped into issues with stack traces, front-end JavaScript errors, regression tracking by release), Grafana+Loki answers "what was the system doing around 1:27" (search over all logs, including normal behaviour). Overlap: both can alert on errors. Claude's view then: not needed yet for a single developer; earns its place with real users or when front-end crash reports are wanted; same third-party PII thought applies. Another session subsequently set Sentry up that afternoon (see [[Session 2026-10-16 (Part 2) — Sentry Setup, Log Correlation, Tools Dashboard]]), and Boris decided Sentry owns error emails.

A branded email would need the Orchestrator itself to send emails (no sender exists yet). Panic alert converted the same way afterwards; Boris noted he cannot see it until a real panic happens.
