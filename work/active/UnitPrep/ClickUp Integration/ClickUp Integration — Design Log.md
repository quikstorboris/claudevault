## Why this exists

Boris uses ClickUp purely as the onboarding task tracker (one list per facility, created from templates). Goal: update tasks from inside OO with a single click instead of switching to ClickUp, and later push structured notes (fees, users, coverage, ...) that OO already knows from Process Street. Explicitly **not crucial** — a convenience integration, built gradually.

A parallel, much bigger want — an Intercom integration with OO-owned UI/UX (Intercom's search, ticket linking and UX are poor) — was discussed in the same session and is **blocked**: it needs an Intercom admin to create a Developer Hub app/token. See "Intercom (deferred)" below.

## Connector vs. integration (the question that started this)

- The **claude.ai ClickUp/Intercom connectors** are MCP servers authorized through Boris's claude.ai account. They exist only inside Claude's tool loop. The UnitPrep backend cannot use that token, nor call through Claude at runtime. So the connectors are a **research/prototyping tool for Claude during sessions**, never a runtime dependency of OO.
- A real OO integration needs OO's own credentials stored in OO. Same pattern as Dropbox and Process Street.
- At the time of the first exploration the ClickUp connector tools were **not visible in the session** (only HubSpot, Intercom, Chrome, etc.). Exploration was done instead via a personal API token and direct REST calls.
- Decision: **do not reuse or scrape the connector's token or Boris's browser session** — fragile and outside what admins approved.

## Decisions (with reasoning)

| # | Decision | Reasoning |
|---|----------|-----------|
| 1 | **ClickUp uses personal API tokens, one per OO user — not a global admin token.** | ClickUp work must be recorded against the person who triggered it. A single shared token would attribute every action to whoever owns it. Boris initially floated a global token, then reversed himself on exactly this point. A personal token acts as the user, so ClickUp's own activity history stays truthful. |
| 2 | **No admin involvement for ClickUp.** | Personal API tokens can be generated by any member (Settings → Apps → API Token). Boris's token worked immediately, so personal tokens are not disabled in the QuikStor workspace. This is the opposite of Intercom. |
| 3 | ~~Token configuration lives in the existing admin Integrations section.~~ **Superseded 2026-10-02 (see decision 13):** per-user integrations live in a new **My Integrations** nav group instead. | The admin-only Integrations section can't host a per-user setting that ordinary users must manage. Kept struck-through for history. |
| 4 | **Red/green status dot next to the ClickUp nav item** showing whether the *current user's* integration is configured and connected. | At-a-glance health; also drives disabling ClickUp actions elsewhere. Connected = token present AND last validation (`GET /user`) succeeded. A 401 on any call flips it red. |
| 5 | **Token storage: dedicated encrypted table, ChaCha20-Poly1305, its own key, RLS restricting each row to its owner; token never returned to the browser.** Table roughly `client_ops.user_clickup_credentials` keyed by OO user, also storing the ClickUp user id/name and last-validated timestamp. | Same crypto pattern as `client_ops.dropbox_configuration`. Backend decrypts only at call time for the acting user. Boris approved the storage suggestion explicitly. |
| 6 | **On save, validate with `GET /user`**, show "connected as <name>". | Fail fast on typos/revoked tokens; gives the dot its truth source. |
| 7 | **Shared vs. personal split.** Shared (non-secret): client/facility → ClickUp list link, resolved task-ID mappings. Personal: the API calls themselves, always made with the acting user's token. | Whoever resolves a task match first benefits everyone; credentials stay individual. A user with no token sees ClickUp actions disabled with a "connect ClickUp" prompt. |
| 8 | **Every ClickUp write is audited in OO** (acting OO user, ClickUp task id, action) in addition to ClickUp's own history. | Attribution is the entire reason for per-user tokens. |
| 9 | ~~Deferred: manager-grantable ClickUp permission.~~ **Promoted 2026-10-02 (see decision 14):** department managers grant access to each integration per user, and that gates the My Integrations menu. | Boris wants this as the core access model for personal integrations, not a later add-on. Still no general delegable-permission framework exists — building one (or a narrow per-integration grant table) is now part of this work. |
| 10 | **Fuzzy task matching resolves ambiguity through the user, not heuristics.** When several tasks share a name, show each with its **parent task's name**; the user picks one, several, or all to update. Design details deferred until building it. | Confirmed in the live data that names repeat (see findings). A wrong silent match would write to the wrong task under the user's name — worse than one extra click. |
| 11 | **Store the resolved ClickUp task id once matched** (per facility, per canonical onboarding step), so later one-click updates are exact-ID calls. | Avoids re-fuzzy-matching on every action; makes the common path deterministic. Proposed by Claude, not yet explicitly confirmed by Boris — treat as a working assumption. |
| 12 | **ClickUp UI surfaces mostly live in the Onboarding Work tab, and "throughout OO"; design emerges gradually.** | Boris: "design will emerge gradually as we add things." Don't over-design up front. |
| 13 | **New left-nav group "My Integrations"** (separate from the admin Integrations group) holding per-user integrations: ClickUp first, then Intercom, HubSpot, and possibly more. Each integration's sub-menu (with its own red/green connection dot) appears only if the user has been granted it. **If the user has no grants, the whole My Integrations group is hidden.** | Cleanly separates shared/admin system credentials (Process Street, DropBox — admin-only, unchanged) from personal credentials each user owns. Hiding the group when empty keeps the nav uncluttered for users who don't use any. Token configuration for each integration is done inside its My Integrations sub-page. |
| 14 | **Access model: the department manager role grants each integration to each user.** Grant = the sub-menu becomes available; no grant = absent. | Managers know who needs which tool; avoids admin bottleneck. Requires a per-user, per-integration grant mechanism plus a way for the manager role to administer it — no such framework exists today (see open questions). |
| 15 | **Dashboard tiles: OO renders its own notes tiles with a Copy button; the user pastes into ClickUp manually.** What is automated is *gathering* the data (from Process Street first, client data files later), not the write into ClickUp. | ClickUp has no dashboard API (see limitation section), so automating the write is impossible; automating the expensive part — assembling the content — keeps most of the value. Design details emerge as the data-gathering framework is built. |

## Required task actions (v1 scope)

Status change, due date, comment, create task under a given **group**. Reads needed to support these: list tasks (paginated), list custom fields.

"Group" resolved by exploration: it is the **"Onboarding Phase" dropdown custom field**, which the List view groups by (13 options: Day 0, Key Dates, Scheduling, Show Stoppers, Texting, SetUp, Finalize, Migration, Launch, Optimize, Explore, Website, plus an option whose emoji name is mangled in the API output). So "create task under a group" = create the task with that custom field set. Subtasks use the `parent` task link. (Earlier worry that groups might be statuses was wrong — statuses are a separate per-list set.)

## Live API exploration findings (2026-10-02)

Done with read-only GETs only, using Boris's personal token. Example list: `Affordable Storage Synott`, list id `901418685125`, workspace id `8413555` ("QuikStor").

**Hierarchy:** Space "QMS Onboarding" → Folder per client (e.g. "Affordable Storage - Beau Ryan") → List per facility. The `80rbk-81594` in a pasted URL is the **List view id**; `GET /api/v2/view/{id}` returns `parent.id` = the real list id. The list's second view `80rbk-81614` is the Dashboard.

**Auth header:** `Authorization: pk_...` — no `Bearer`.

**Statuses are per-list** (this list: to do, ready for you, in progress, unclear, update required, waiting on, critical issue, complete). Never hard-code status names; read them from the list. Statuses can differ between templates.

**Custom fields on this list:** Onboarding Phase (the grouping), QMS Area (15 options), Corp/Fac (Corporate/Facility), Product (7 options), Role (U.S. Implementation, Hermie, Serbia, Philippines), Business Name, Requesting Client, TASKMASTER Version #, Submit Here (url), Publish date. Custom-field values on a task come back as dropdown **indexes**, not names — must map through the field's `type_config.options`.

**Pagination:** the task list endpoint returns 100 per page (0-indexed `page`); this list had 110 tasks including subtasks. Must paginate. Use `subtasks=true&include_closed=true`.

**Names repeat, and prefixes vary** — this is the matching problem. Examples seen in one list: "ADD Recurring Fees" appears twice (different QMS Area), "CREATE Default User Roles" vs "CONFIGURE Default User Roles", "ADD Security Deposit" vs "ADD Security Deposits". Parent tasks carry numeric/emoji prefixes ("2. 👥 CONFIGURE Users", "3.💲CONFIGURE Fees, Security Deposits & Taxes", "🦕PERFORM ..."). Matching needs prefix/emoji normalization and parent context; name alone is ambiguous. Different templates use different names, so the canonical-step registry (like the vendor-format registry) needs aliases per template.

**Encoding gotcha:** many emoji in option and status names come back as broken surrogate pairs (`\udc..`) from the API when printed through some tools — use stable ids/indexes, never display-name round-tripping, for matching and writing.

**Docs API (v3) exists and works:** `GET /api/v3/workspaces/{id}/docs` returns docs. Probing the example list and its folder found **no Docs attached** — so the dashboard tiles are not Docs.

## Hard limitation: ClickUp Dashboards have no API

- The Dashboard tab is a **view of type `dashboard`**. `GET /view/80rbk-81614` returns only generic view metadata (grouping/filter/column settings) — nothing about cards.
- `GET /view/{id}/task` on it returns `400 "Must be a task view"`.
- Probes of `/v2/team/{id}/dashboard` and `/v3/workspaces/{id}/dashboards` returned `404`.
- Conclusion (as of this probe): **the public API cannot create, read or write dashboard cards/tiles.** That means (a) auto-creating the notes tiles via API is not possible, and (b) even if tiles are created manually first, there is no known API to write text into them.
- Possible exception to verify: if some tiles are actually backed by a writable object (a Doc embed, a task, a custom field, a list/view card), the backing object might be writable even though the dashboard isn't. **Open question to Boris: what card types are the Notes / Conversion Parameters / Users & Roles / Coverage / Delinquency Policy / Fees tiles?**
- The ClickUp web app itself uses internal, undocumented endpoints for dashboards. Not pursued: unsupported, can break without notice, and likely needs browser-session auth rather than the API token.

### Options if tiles stay unwritable

1. **OO is the source of truth for the structured notes** (from Process Street, later from client data files) and shows them in OO's own UI; ClickUp tiles remain a manual convenience.
2. **OO generates a ClickUp Doc per facility** with the same sections, updated via the v3 Docs API (visible inside ClickUp, less pretty than tiles).
3. **Leave tiles manual**, automate only task actions.
Claude's recommendation: 1 plus task actions first; consider 2 later if the team needs the notes inside ClickUp. Not yet decided by Boris.

## Notes content sources (from Boris)

- Some tile content can come **directly from Process Street** (fees, users, coverage, ...) — straightforward given the existing PS integration.
- Some would have to come from **client data files** — a heavier lift; deferred until a framework exists.
- Any generated content must go into clearly **marked managed sections** so a re-sync never overwrites hand-written notes.

## Future / backlog

- **Per-client dashboard in OO listing tasks with upcoming due dates** (Boris, 2026-10-02: "probably down the line"). Cross-client rollup of due-soon tasks, sourced from ClickUp via the stored list links. Not scheduled.
- Manager-granted per-user integration access (decisions 13–14) — needs a grant mechanism designed first; likely the first piece to build, since My Integrations visibility depends on it.
- Dashboard tile automation in ClickUp — blocked on ClickUp API support; replaced by OO-rendered tiles with Copy buttons (decision 15).

## Open questions

0. **Grant framework design** (new, from decisions 13–14): per-user per-integration grant table vs. new permissions per integration; what exactly the department-manager role may do (grant only within their own department? revoke?); how "department" is modeled today (it may not be at all — needs checking against the Roles & Permissions design before assuming); how grants interact with RLS and with the `integrations.manage` admin permission; whether a granted-but-unconfigured integration shows a red dot (yes, assumed).

1. **Tile types** on the existing dashboards (decides whether any tile content is API-writable).
2. ~~Who may set a token?~~ **Resolved 2026-10-02:** My Integrations group + manager-granted per-user access (decisions 13–14).
3. **List discovery:** how a client/facility gets linked to its ClickUp list (paste the list URL once? search under the client's folder?). Not yet discussed.
4. **Canonical step registry:** which onboarding steps matter first for one-click updates, and the alias patterns across template variants.
5. **Rate limits:** ClickUp's v2 limit is ~100 req/min per token; per-user tokens make this a non-issue unless we do bulk sync, but caching list reads is still wise.

## Intercom (deferred)

- Use case is large: sync Intercom conversations/contacts/companies into OO, add real search (Postgres full-text), ticket-to-client/facility linking, a client-centered timeline — so Boris rarely needs Intercom's UI.
- **Blocked:** requires an Intercom admin to create a Developer Hub app. Boris deliberately will **not** approach admins until OO has shown its value — doing so "raises questions." Decision: wait; don't draft the request yet.
- Notes for when it's unblocked: scope the app minimally (read conversations/contacts/companies; notes/tags later), consider webhooks (needs a public URL + signature verification), and treat synced conversations as PII under the same RLS discipline as the rest of `client_ops`.
- Meanwhile the Claude Intercom connector can be used in sessions to study real data shapes for schema design, as prototyping only.

## Security notes

- Boris pasted his ClickUp personal token into the chat on 2026-10-02 (after being told to enter it only into OO's settings page once built). **The token is therefore in that session's transcript.** It was used only for read-only GETs, never written to any file or to this vault. **Rotate/regenerate it once the OO settings page exists and the token is stored there.** A personal token has the user's full access to every workspace they belong to — treat as a password.
- Never log request headers containing the `Authorization` token; redact in any error reporting.
