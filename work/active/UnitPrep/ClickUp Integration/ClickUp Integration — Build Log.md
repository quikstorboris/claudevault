### What was built (all uncommitted in the WSL repos at time of writing; nothing pushed or tagged)

**unitprep-api**
- Migration `20261002180000_add_user_permission_grants`: `auth.permissions` gained `category` (dialog grouping, data not code) and `directly_grantable` (default false). New table `auth.user_permissions (user_id, permission_key, granted_at, granted_by)`. New permissions `integrations.clickup` (category "Integrations", directly grantable) and `user_permissions.manage` (admin only, not grantable).
- **Safety design:** (1) a trigger (`auth.enforce_directly_grantable`) refuses any grant of a permission not flagged `directly_grantable` — so this mechanism can never hand out `users.manage_roles`, `integrations.manage`, etc.; (2) RLS: only `admin` or `department_manager` may insert/delete grants, never on one's own account; (3) the handler requires `user_permissions.manage` (admin only today). RLS already permits `department_manager`, so extending to dept managers later is one `role_permissions` row **plus** opening the Users page/list function to them (see open items).
- `auth.resolve_session` now **unions direct grants into the resolved permission set**, so every existing `require_permission` call and the frontend (which only sees the resolved list) work unchanged, and grants take effect on the target's next request.
- Migration `20261002190000_create_user_clickup_credentials`: `integrations.user_clickup_credentials` — one row per user; token stored only as ChaCha20-Poly1305 ciphertext (`integrations::secrets`, **AAD bound to the user id**); status `valid|invalid`; ClickUp user id/name; RLS = owner's own row only for every operation, **not even admins can read another user's row**.
- Endpoints: `GET /auth/users/{id}/permissions`, `PUT|DELETE /auth/users/{id}/permissions/{key}` (idempotent, audited as `permission_granted/revoked` with before/after sets); `GET /integrations/clickup/connection`, `PUT|DELETE /integrations/clickup/token`, `POST /integrations/clickup/test` (all need `integrations.clickup`). Saving validates against ClickUp first (`GET /user` + `GET /team`) — **a token ClickUp rejects is never stored**; the response never echoes the token; an unreachable ClickUp returns 502 and does **not** flip a stored token to invalid (only a real 401 does). New audit events: `permission_granted`, `permission_revoked`, `integration_connected`, `integration_disconnected`.
- The ClickUp base URL is overridable via an env seam **only under `cfg(test)`**, so a stray env var can never redirect users' tokens to another host in a real build.
- Tests: full workspace suite green (716 passed at the time). Six new `#[ignore]`d real-DB tests (`clickup_db_*`, run against the local throwaway Docker `test-db` as `app_service` so RLS genuinely applies) cover: grant unioned into `resolve_session`; trigger refuses role-only permissions; RLS (non-granter denied, admin allowed, self-grant denied); credential RLS isolation even from admins; the full connection lifecycle against a mock ClickUp (reject → not stored, save, ciphertext not plaintext, revoke → invalid, recover, remove, test-with-nothing = 404); grant endpoints idempotent + role-only permission refused. A mock-ClickUp HTTP test also confirms the token is sent raw (no `Bearer`). The route manifest + `permission_gate_tests` cover the new routes automatically. Run the DB tests with `TEST_DATABASE_URL=postgres://app_service:app_service@127.0.0.1:5433/unitprep_test cargo test --bin unitprep -- --ignored clickup_db` after `scripts/bootstrap_test_db.sh`.
- Applied to the **Neon dev** database only (not prod). Boris's own user was granted `integrations.clickup` by direct SQL on dev (`granted_by` NULL = bootstrap; the RLS correctly forbids self-grants through the app). No token stored.

**unitprep-ui**

Status lives in a shared module store keyed by user id so the page and nav stay in sync and one user's state never leaks to another on the same tab.

### Decisions made during the build (with reasoning)
- **Direct grants are a separate mechanism from roles, not new roles.** A role per integration per team would explode the role list; whether someone has ClickUp is a per-person call.
- **Role editing moved from the row into the dialog** (Boris specified roles as a dialog section). Role assignment stays admin-only at the database (`user_roles` RLS) for now.
- **Idempotent PUT/DELETE for grants** (unlike role grants, which 409 on duplicates) because the dialog is a set of checkboxes — "make it so" semantics.
- **Frontend gating is UX only**; the backend and RLS are the boundary. The ClickUp page fetches nothing unless the user holds the permission.

### Open items surfaced
1. **Department managers cannot use the dialog yet.** `auth.list_users_for_admin()` and `user_roles` RLS are admin-only, and the Users page needs `users.manage` (admin) — so a dept manager can't even see the page. Making them real granters needs: a way for the page/list to be visible to them *without* handing them invite/deactivate/recover powers, plus a decision on which roles a dept manager may assign (proposal: only roles whose permissions are a subset of their own, to prevent escalation). Needs Boris's call.
2. **The "active" status label is misleading** (Boris, 2026-10-02: an "active" user "Invite Test" shows a Recover account button). `active` means *enrolled and not deactivated* — it says nothing about being signed in or recently seen; the "Last active" column carries that. The Recover button is for an enrolled user who lost their passkey (it revokes passkeys/TOTP/sessions and issues a fresh setup link). Candidate fix: rename statuses in the UI (invited → "Invited", active → "Enrolled", deactivated → "Disabled") and/or clarify the button. Not changed yet.
3. Commit/tag/push for both repos not done; the running API must be restarted to pick up the new routes.
4. Next ClickUp steps once Boris has connected his token: read client list tasks (paginated; custom-field values come back as option indexes), resolve a list from a pasted URL/view id, the ambiguous-name picker UI (shows parent task names), then status / due date / comment / create-under-phase actions.

## Design — Link ClickUp to companies/facilities (2026-10-02, after the release above)

Boris's request: on the **company page → Company Info** a **Link ClickUp** button; it searches ClickUp and presents options, with fuzzy matching because names differ between ClickUp and Process Street/OO. For multi-facility clients (e.g. Affordable Storage) each OO facility is auto-matched to a ClickUp list; the user **confirms**; each row has a dropdown to change the mapping and a **Link manually** button to paste the list URL from ClickUp. Afterwards each **facility page → General tab** gets a **ClickUp** button (under Website) that opens the list, with a red/green dot, plus a re-link action.

### What the live ClickUp data looks like (read-only survey, QMS Onboarding space)
- 292 folders, 816 lists (one API call returns the whole hierarchy). **Folder ≈ company, list ≈ facility** — but the folder name is often the *legal entity* ("1659 Birchwood LLC" holds the list "Northwest Heated Mini-Storage"), so the **facility→list match is primary and the folder name is only a hint.**
- Many lists are not facilities ("Post-Onboarding - …", "Pre-Onboarding Training", "🎈 … Template", "SANDBOX…", "zzz…", "GENERAL/Multiple Sites"). **Boris: not needed, ever → exclude them entirely** (no "Other lists" section).
- ~684 facility-like lists; 230 folders have exactly one; a few have 25–30 (Absolute Management, Advance Management).
- Only ~7 company-level "General / Multiple Sites"-style lists exist (Advance Management, Laredo, Menards, Occidental, Pankey, Trojan, …) — these are *excluded as non-facility lists*. Whether several OO facilities ever share one real list is unclear (e.g. Dubuqueland's "Upper Lot" has no obviously separate list) → **default one list ↔ one facility, but allow many-to-one with a warning, not a block.**

### Prototype matcher against the 30 real OO facilities (throwaway Python, not in the repo)
Token-set overlap + sequence ratio on normalized names (drop LLC/Inc/"self storage"/punctuation, "&"→"and"), plus a small folder-name nudge. **~27 of 30 top-1 correct on first try.** Affordable Storage's nine facilities all matched their lists exactly. The misses and what they teach:
- "Affordable Storage, LLC" (Thibodaux, LA) → the real list is "Affordable Storage (Thibodaux, LA)", but the matcher preferred "Affordable Self Storage": **the facility's city/state must be a positive signal** (list names often carry them).
- Facility "Dubuqueland Mini Storage - Upper Lot" ambiguous between "Dubuqueland Mini Storage" and "… Parking": genuinely needs the human confirm step.
- A typo'd OO name ("…Storage, LCC") still matched at 0.88 — normalization is forgiving enough.

### Decisions
- **Scope:** QMS Onboarding space only (looked up by *name*, held as data, not a hardcoded id).
- **Dot meaning:** green = *linked and usable by me* (list linked **and** my own ClickUp token works); red = not linked / list gone / my token rejected; grey = I have no ClickUp access or status unknown.
- **Manual link:** paste the ClickUp list URL; Orchestrator resolves it (list URL or view URL) with the user's token and shows the list's real name before it counts. A **"?" tooltip** on/next to "Link manually" explains how to copy the facility list's URL from ClickUp.
- **Unlink:** per facility (General tab) and **Unlink All Facilities** (company info). Re-link action named **Change link** (separate from Unlink).
- Nothing is auto-saved: auto-matches are suggestions the user confirms; low-confidence rows are highlighted and unchecked.
- The ClickUp hierarchy is fetched once per user and cached briefly server-side; fuzzy matching runs inside Orchestrator (no per-keystroke ClickUp calls, no rate-limit pressure).

## Build log — 2026-10-02 (third pass): Link ClickUp, built

Built the design above. **Uncommitted** in both WSL repos at the time of writing (api would be v1.9.60, ui v1.6.56 when released); migration `20261002210000_add_facility_clickup_links` applied to **Neon dev only**.

### Backend (`unitprep-api`)
- **Storage:** nullable columns on `clients.facilities` — `clickup_list_id/name/url`, `clickup_folder_name`, `clickup_linked_by/at` — with a CHECK that they are all-set-or-all-null, plus a partial index on the list id. Only the list **id** is authoritative; name/folder/URL are a snapshot taken at link time. **No unique index on the list id**: many-to-one is allowed (the live data suggests one list per facility, but a shared list is plausible) and the API *reports* it instead of blocking. Process Street re-syncs never touch these columns. New singleton `integrations.clickup_settings(onboarding_space_name = 'QMS Onboarding')`, readable by any authenticated user, writable by admin/developer — the space is found **by name** at runtime, no ClickUp ids hardcoded.
- **ClickUp client** now also reads teams, spaces, folders (whole onboarding hierarchy in one call), a list, and a *view's* parent list. **Real-API gotcha found by probing:** ClickUp returns HTTP **401** both for a bad token (`OAUTH_025`) *and* for "that list doesn't exist / you can't see it" (`OAUTH_027`); views return 404 `ACCESS_118`. The client now distinguishes them, so a mistyped list URL can never flip a good token to "invalid" (there is a test for exactly this).
- **Pasted-URL parser** (`clickup::url`): accepts `/v/li/<listId>`, `/v/l/li/<listId>`, `/v/l/<viewId>` (what the address bar shows on a list's List/Dashboard tab — resolved to its parent list through the API) and a bare list id; refuses other hosts (including look-alikes like `app.clickup.com.evil.test`), folders, tasks and docs with a message saying what to paste instead.
- **Matcher** (`clickup::matching`) — see the prototype section above; ported with **IDF-weighted token overlap** (rare words like a city or street name count far more than "affordable"), the facility's **city folded into the query**, a **small legal-entity-to-folder bonus** (never primary), generic words dropped, typo-tolerant bigram Dice, and **non-facility lists excluded** (Post-/Pre-Onboarding, templates, sandboxes, "General / Multiple Sites", training, demo, …). Confidence = High needs score ≥ 0.9 **and** ≥ 0.15 margin over the runner-up; anything with a close second place is at most Medium. Tests use a slice of the **real** onboarding hierarchy: all 9 Affordable Storage facilities match their own list with High; "Affordable Storage, LLC" (Thibodaux) beats the lookalike "Affordable Self Storage" but is *not* High; legal-entity folders (East 630 LLC, Sprenger & Sprenger) don't break the facility match; "LCC" typo still matches.
- **One list per facility, suggestion-side** (`clickup::assignment`): after ranking, the facility with the stronger claim keeps a contested list and the other falls back to its next candidate or to no suggestion (the Dubuqueland main facility vs "Upper Lot" case). A person can still deliberately point two facilities at one list.
- **Endpoints** (all need the per-user `integrations.clickup`, all use the caller's own token): `GET /integrations/clickup/lists` (dropdown catalog), `POST /integrations/clickup/resolve-url`, `GET /clients/{company}/clickup/suggestions`, `PUT /clients/{company}/clickup/links` (all-or-nothing batch: every list **re-verified with ClickUp and its name/URL taken from ClickUp, not the browser**; a list outside the onboarding space is refused; nothing is saved if any is bad; reports `shared_lists`), `DELETE …/facilities/{id}/clickup-link`, `DELETE …/clickup/links` (**Unlink All Facilities**). Unlinking makes **no ClickUp call**, so a stale link can be removed even when the user's token is dead. The hierarchy is cached 5 min per user and dropped when they replace/remove their token.
- **RLS honesty:** facility writes still need a client-ops role; RLS narrows an UPDATE to zero rows for others, which now surfaces as a clear **403** (a first version used `SELECT … FOR UPDATE`, which RLS hid, giving a misleading "no such facility" 404 — caught by a test and fixed). Audited as `facility_clickup_linked` / `facility_clickup_unlinked` (before/after list id).
- Company and facility detail responses now carry the link fields.
- **Tests:** 761 unit/gate tests (the route manifest proves every new route 403s without the permission) + 8 new real-DB tests against a mock ClickUp (suggestions, dropdown catalog hides non-facility lists, URL resolution incl. wrong space/nonexistent/folder, save stores ClickUp-reported name/URL, all-or-nothing, cross-company facility refused, no-client-ops-role → 403 for save *and* unlink, shared-list warning, unlink works with a dead token, never-connected user told to connect).

## Build log — 2026-10-05: first automation — post a duplicate check to its ClickUp task

Boris's spec: after the dedup check completes and the summary file is saved into the client's Dropbox folder, OO finds the facility's ClickUp task for that check (`COMPLETE Duplicate Tenant Corrections` for the 1st check, `PERFORM 2nd Duplicate Check` for the 2nd — names vary, so match loosely), **always asks** (even for one match; radio buttons for several), then (1) comments "Duplicate check results are here" with *here* linking the saved file in Dropbox, (2) sets the task complete, (3) assigns the acting user. Status as of 2026-10-05: **built and tested, uncommitted** in both WSL repos; migration `20261005130000` applied to the local test-db only (not Neon dev, not prod).

### How it works
- **Which check is it** comes from OO, not the browser: the dedup run's position among the facility's dedup runs in `client_ops.tool_runs` (`ROW_NUMBER` by `created_at`; 1 → first-check step, 2+ → second-check step). Where the file went = the run's `output_dropbox_path`; which list = the facility's stored ClickUp link. The browser sends only the session id and, to update, the task the person confirmed.
- **Matching is data-driven**: new table `integrations.clickup_task_steps` (`dedup_first`, `dedup_second`: label, ordinal, name phrases; readable by all, editable by admin/developer — no editing UI yet). `clickup::task_matching` scores each task in the list against the phrases by word overlap, ignoring verbs (perform/complete/run), numbering, emoji and plurals; an ordinal mismatch ("2nd" task for the 1st check) is penalized ×0.4; ≥0.4 is offered, top 10, subtask beats an equally-scored parent section. Each candidate shows its parent task's name, status, assignees and an Open-in-ClickUp link.
- **Endpoints** (both need `integrations.clickup`): `GET /clients/{c}/facilities/{f}/clickup/duplicate-check-tasks?session_id=` and `POST .../clickup/duplicate-check-results {session_id, task_id}`. The POST re-reads the task from ClickUp and refuses (400, nothing written) unless it is in the facility's linked list, and refuses (409, nothing written) when the list has no complete status. Then three separate ClickUp calls (comment → add assignee → set status); each reports its own outcome since they cannot be atomic. Audited as `facility_clickup_duplicate_check_posted`.
- **Complete status** is read from the list (name "complete"/"completed", else the `closed` class, else `done`) — never hard-coded (statuses are per list).
- **Dropbox link**: new `DropboxClient::shared_link` (`sharing/create_shared_link_with_settings`, reusing an existing link on `shared_link_already_exists`). Needs the Dropbox app's **`sharing.write` scope — not verified**; if Dropbox refuses, the comment falls back to the file's plain `dropbox.com/home/<path>?preview=<file>` URL (opens for anyone with folder access) and the UI says so.
- **UI**: `ClickUpDuplicateCheckPanel` appears on the dedup results page once the file is saved to Dropbox (only for users with `integrations.clickup`); "Update ClickUp task" / "Not now"; shows ✓/✗ per step afterwards.

### Decisions I made without asking (flip any of them)
- "Assignee set to the user" = the user is **added**; existing assignees stay (removing others felt destructive).
- Only the saved-to-Dropbox path triggers it (a browser download has no link to share). Not yet offered from the Onboarding Work tab for past runs — the endpoints take a session id, so that is a small follow-up.
- 3rd and later checks use the 2nd-check step.
- Comment text is fixed ("Duplicate check results are here"), not configurable.
