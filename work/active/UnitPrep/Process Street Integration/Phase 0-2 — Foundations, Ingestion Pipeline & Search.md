# Phase 0-2 — Foundations, Ingestion Pipeline & Search

Full build detail for [[Implementation Plan]]'s Phase 0-2 headers, split out here once the plan note crossed this vault's organization-size threshold. Historical/shipped — not touched again after 2026-08-31 except where a later session's fix is cross-linked.

## Phase 0 — Foundations (no user-facing feature yet) — **shipped 2026-08-28**

- Migration `20260828120000_create_process_street_client_tables` created a **new `clients` schema** — `companies`, `facilities`, `facility_policies` + its 5 category tables (`policy_fees`, `policy_taxes`, `policy_delinquency_steps`, `policy_coverage_tiers`, `policy_commission`, `policy_specials`), `people`/`facility_people`, `facility_merchant_accounts`, `facility_contract_orders`, `ps_task_status` — all 14 tables. (`policy_copy_events` was dropped in favor of reusing the existing `client_ops.audit_log`.) Went back and forth on the schema question once for real reasons (briefly landed in the existing `client_ops` schema, then Boris asked for a genuine opinion rather than deference, and a fresh schema turned out to be the better call — see [[Client & Facility Schema (Process Street-Sourced)]] for the full reasoning). Applied and verified on the Neon dev branch, including a companion update to `scripts/setup_app_service_role.sql` granting `app_service` access to the new schema.
- RLS policies scoped by role, matching the codebase's own established pattern (e.g. `client_ops.vendor_format`'s) — SELECT authenticated-only, mutations gated to `onboarding_manager`/`department_manager` (not admin, matching that role's own "never performs client operations" description; reuses the existing `client_ops.perform` permission rather than a new one, since schema location doesn't change which capability is being gated). Verified live, not just by policy count — twice, once for each schema attempt.
- A read-only `ProcessStreetClient` Rust module (`src/process_street/`), mirroring `src/dropbox/`'s existing shape — pagination-following helpers for `/workflows`, `/workflow-runs`, `/workflow-runs/{id}/tasks`, `/workflow-runs/{id}/form-fields`, 4 unit tests against real captured JSON. No write methods exist, by design.
- PS API key: turned out simpler than expected — Dropbox's own config (`src/dropbox/config.rs`) is just a plain env var, no encryption-at-rest infrastructure, since it's a single org-wide secret rather than a per-client credential like the QMS case. `ProcessStreetConfig` follows the same precedent (`PROCESS_STREET_API_KEY` env var).
- Full detail, including how RLS was actually verified (not just asserted), in [[Client & Facility Schema (Process Street-Sourced)]]'s "Phase 0, shipped" section.

## Phase 1 — Full ingestion pipeline (backend only, no UI) — **shipped 2026-08-28, Contract Order mapping added 2026-08-31**

- The mapping/ETL layer shipped: `src/clients/intake_mapping.rs` and `src/clients/merchant_account_mapping.rs` map real PS field keys → the schema, with known-type tagging (`fee_type`/`step_type`) and a denylist-based `raw_ps_snapshot` sanitizer for the sensitive workflow. `src/clients/repository.rs` writes the mapped output into Postgres inside a real RLS transaction (`auth::begin_rls_transaction`).
- **Scope grew mid-phase**: pulling the New Merchant Account workflow's full field list (not just the handful of fields checked earlier) surfaced real SSN/DOB/home-address/bank-account/EIN/system-credential data for Prairie Enterprises' real owners. This is the exact trigger the 2026-08-07 PII/compliance review anticipated in advance — see `src/clients/encryption.rs` and migration `20260828130000_add_merchant_account_encrypted_pii`. Field-level encryption (ChaCha20-Poly1305, mirroring `auth::totp`'s existing pattern) now protects this data; RLS on the two Merchant Account tables was also tightened to `onboarding_manager`/`department_manager` only (not the blanket "any authenticated" every other `clients` table uses).
- `ps_task_status` population from `/tasks` — built (`repository::upsert_task_status`), upserts on `(facility_id, workflow, ps_task_id)`.
- **Real end-to-end verification against the actual Neon dev database**, not a mock: `clients::repository::integration_tests::highway20_golden_fixture_ingests_and_round_trips_through_real_postgres` (an `#[ignore]`d test, run explicitly) ingests the real Highway 20 Intake fixture + a sanitized-but-realistic Merchant Account fixture through the real mapping → repository → RLS-transaction path, decrypts the encrypted columns back out of real Postgres and confirms they match, then rolls back so nothing persists. Caught and fixed a real bug this way: `app_service` had table grants but no sequence grants for the schema's several BIGSERIAL-keyed tables (`GRANT ... ON ALL TABLES` doesn't cover a sequence, a separate grantable object) — fixed in `scripts/setup_app_service_role.sql`; worth checking `client_ops.vendor_format` (also BIGSERIAL) for the same latent gap separately.
- **The trigger itself**: `src/clients/ingest.rs::ingest_facility` — given a facility's known PS run ids (Intake required, Merchant Account and Contract Order both optional), calls the live API via `ProcessStreetClient`, maps, and writes everything in one transaction (commits only if every step succeeds).
- **Contract Order mapping shipped 2026-08-31** (`src/clients/contract_order_mapping.rs`), using real data from two real clients Boris pointed at directly — Tri County Mini Storage and Dubuqueland Mini Storage. Finding this data surfaced a real, important bug: `GET /workflow-runs` defaults to `status=Active` only, and Contract Order runs are marked `Completed` once processed, so the original Active-only search found neither client. Fixed at the source in `ProcessStreetClient::list_workflow_runs`, which now queries Active + Completed + Archived and merges them — see [[Gotchas#Process Street's `GET /workflow-runs` defaults to `status=Active` only — silently hides most real data|the vault Gotchas entry]]. Only `migrating_from_system` is promoted to a named column (the field Boris flagged as operationally important); the real run has ~99 fields (rate quoted, processor, POC, shipping/payment-form checklists) all still recoverable from `raw_ps_snapshot` if a future tab needs them as real columns. Proven against real Postgres too — the golden-fixture integration test now also exercises `ingest_contract_order_run`.
- **Committed, tagged, and pushed 2026-08-31**: 14 commits total (`03db4c1..b3609e6`) on `origin/main`, tagged `v1.8.13` (annotated, matching the repo's existing tag convention). `unitprep-api` clean sync with origin, no divergence.
- **Contract Order explicitly on hold** per Boris, 2026-08-31 — `migrating_from_system` has now been checked against two real clients (Tri County, Dubuqueland) and was blank on both; paused until he finds a real client where it's actually answered, rather than guessing at what a filled value looks like. The mapping/repository/ingest code is already shipped and won't need rework when that example turns up — it'll just need adding to a future ingestion call's `contract_order_run_id` argument.
- **Real-world data-quality finding along the way**: PS's "Owner/District Manager/Manager Level Users" free-text field has at least two genuinely different human-entered formats in production — comma-separated one-line-per-person (Beau Ryan's facilities) and multi-line blank-line-separated per person (Prairie Enterprises). `people::parse_people_block` detects and handles both. Confirms Boris's own instinct that this needed a real comb-through, not an assumed single format.

## Phase 2 — Search — **facility-name half shipped 2026-08-31, sequenced ahead of person-name search per Boris's own call**

- **Better than planned**: PS's `/workflow-runs` has a real, working server-side `name` filter (case-insensitive substring, confirmed directly against the live API) — no pre-sync/cache needed at all for facility-name search, just a live filtered call. `ProcessStreetClient::search_workflow_runs_by_name` (searches Active+Completed+Archived, same fix as `list_workflow_runs`) + `clients::search::search_by_facility_name`.
- **Narrowed to Intake-only, 2026-08-31** (superseding the original "searches all three workflows at once" shipped this same day) — not every client uses Elavon, so searching Merchant Account/Contract Order too made "no match there" look like "doesn't exist" rather than "doesn't use Elavon."
- **Confirmed the same facility genuinely has a different run title per workflow** — Highway 20 is `"Highway 20 Self Storage - QMS Onboarding"` on Intake but `"Prairie Enterprises (Highway 20)"` on New Merchant Account. Relevant again for Merchant Account matching (Phase 3), since that's exactly the mismatch it has to work around.
- **Side discovery while testing this**: Highway 20 does have a real Contract Order run after all (`Order for Highway 20 Self Storage`) — the earlier "Highway 20 has no Contract Order run" belief was itself a casualty of the status=Active-only bug. Its `migrating_from_system` field is filled in for the first time seen this integration: **"Sentinel Winsen."** Contract Order work stays on hold per Boris's 2026-08-31 call regardless — this surfaced as a side effect of search testing, not new Contract Order work — but this is the real example that call was waiting for, whenever he wants to pick it back up.
- **Not yet built (as of 2026-08-31)**: person-name search (finding a facility by an owner/DM/manager's name) — still needs its own lightweight background sync, since PS has no equivalent server-side search over form-field values. Sequenced deliberately after facility-name search per Boris, 2026-08-31. Still not built as of the 2026-09-02/03 session — see [[Session 2026-09-02–03 — Confirmation Screen, Re-sync, Activity Logs & Client Record UI]].
