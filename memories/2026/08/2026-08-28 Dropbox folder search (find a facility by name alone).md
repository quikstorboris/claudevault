# Dropbox folder search (find a facility by name alone) shipped via Dropbox's native search_v2 — no cache built

Follow-up to Orchestrator's Dropbox client (Phase 1 foundation) is built and verified against the real API and the folder-picker memory. Boris asked for the picker to support finding a facility folder by name alone (client corporate names and facility DBA/geographic names often don't match, so browsing client-by-client can't find a facility whose name you know but whose client you don't), and to decide whether that needed a custom cache before building it ("check before building").

**Verified before building**: Dropbox's `files/search_v2` solves this natively, recursively, server-side -- no custom tree-walk/cache/Redis needed (see Redis is overkill for Orchestrator today — trigger for the adjacent Redis decision made in the same conversation). Confirmed live against the real QMS Onboarding folder: searching "Highway 20" (facility name only, not knowing client "Prairie Enterprises LLC") found the exact facility folder among 48 total matches, and searching "Prairie" (client name only) found the client folder. Latency ~250-270ms per call, fine for debounced real-time search. The one real wrinkle: Dropbox has no "folders only" filter -- every query also matches file names (rent rolls, unit CSVs, templates), so the real facility folder was buried past the top 20 results at Dropbox's default `max_results`, only appearing once raised to 100. Filtering to `.tag == "folder"` happens after the fact, server-side.

**Implementation** (`unitprep-api`): `DropboxClient::search_folders` (`src/dropbox/client.rs`) proxies `search_v2` scoped to `config.root_path` with `max_results: 100`, filters to folders. New `GET /dropbox/search?q=` (`src/api/dropbox_browse.rs`) -- unlike `/dropbox/list`, needs NO root-boundary check, since the search path is always the client's own configured root, never caller-supplied. Enforces a 2-character minimum query length (server AND client side) since a too-short query risks the real folder being crowded out past the 100-result ceiling before the folder-only filter even sees it. Also fixed `/dropbox/list`'s missing alphabetical sort while touching this code (Dropbox doesn't guarantee order). Real-network coverage added alongside the existing `list_folder` ignored test: `search_folders_finds_a_facility_by_name_alone`, asserting every result is a folder and that "Highway 20" alone surfaces "Highway 20 Self Storage" under "Prairie Enterprises LLC" without naming the client.

**Frontend** (`unitprep-ui`): `DropboxFolderPicker` gained a debounced (300ms) search box, rendering hits as breadcrumb-style "Client ▸ Facility" (computed by stripping a separately-fetched root path from each hit's absolute path_display, since the picker's normal browse state doesn't always know the root -- e.g. when editing an existing selection it starts browsing at that path, not the root). Clicking a hit navigates the browser there rather than selecting immediately, so the existing single "Select this folder" flow stays the only commit path. Hit two real `react-hooks/set-state-in-effect` violations building this (setState directly in an effect body instead of the event handler that changed the triggering state) -- fixed by moving both resets (search-query-cleared-on-open, search-results-cleared-on-short-query) into their respective onClick/onChange handlers, matching this codebase's own already-documented pattern for the same lint rule.

**A live-testing gotcha hit while verifying this**: a stale `target/release/unitprep` process (started by Boris himself via his own `cargo run` release build, pasted into this same conversation much earlier) had been sitting on port 8080 the whole session, silently answering health checks and giving false "the server is up" confirmations while newer `cargo run` (debug) attempts were actually failing to bind and dying immediately. Caught because a route that should have been merely auth-gated (401) instead came back 404 -- impossible for a genuinely-registered route, which is what triggered the investigation. Killing it and restarting, then verifying via actual log content ("Finished `dev` profile", the real listening PID) rather than a bare curl-returns-200 check, fixed it. Earlier same-session verifications that asserted specific NEW log fields/response shapes (the SIGTERM graceful-shutdown lines, sqlx query-timing fields, request-id header matching) remain trustworthy regardless, since old pre-session code could not have produced that exact output -- but the generic "curl /health returns 200 == the right binary is running" pattern this whole session used as a readiness gate is NOT reliable on its own if a stale process might already hold the port. Worth checking log content/PID freshness explicitly next time, not just a 200 status.
