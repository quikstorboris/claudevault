# A .env.local value extracted via grep+cut can carry literal quote characters, breaking tools that validate the value strictly

When a `.env.local`-style file stores a value quote-wrapped -- `KEY="postgres://..."` rather than `KEY=postgres://...` -- extracting it with the common `grep '^KEY=' file | cut -d '=' -f2-` pattern (used because `source`-ing the file directly is unsafe when values contain `&`, see the WSL Execution Technique note) preserves the literal `"` characters in the resulting shell variable. Most consumers of a URL are lenient enough that this goes unnoticed, but a strict one -- sqlx-cli's `--database-url`, seen concretely here -- rejects it outright with a misleading error (`error with configuration: relative URL without a base`), which reads like a malformed or empty URL rather than two stray quote characters.

Fix: strip a leading and trailing `"` after the cut, e.g. `sed -e 's/^"//' -e 's/"$//'`. Cheap, and safe to apply unconditionally -- it's a no-op on a value that was never quoted in the first place.

Generalizes beyond this one file or project: any workflow that shells out to extract a single value from a `.env`-style file with grep+cut, rather than parsing it properly, hits this the moment that particular file happens to quote its values -- which is common (dotenv conventions permit it, and any value containing `#` or leading/trailing whitespace typically needs it). Check the raw line with `grep '^KEY=' file | cut -c1-30` before trusting an extracted value that a downstream tool is rejecting for a reason that doesn't match the visible symptom.
