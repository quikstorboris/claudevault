# Next.js 16's proxy.ts must export a function literally named `proxy` (or a default export) — `middleware` is not recognized in that file

Next.js 16 renamed the `middleware.ts` root convention file to `proxy.ts`, but this isn't just a rename with the same contract carried over silently. The framework's own entrypoint template (`next/dist/build/templates/middleware.js`, verified by reading the compiled source directly since the public docs don't spell this out) resolves the handler as:

```js
const isProxy = page === '/proxy' || page === '/src/proxy';
const handlerUserland = (isProxy ? mod.proxy : mod.middleware) || mod.default;
```

So in a file named `proxy.ts`, only `export function proxy(request: NextRequest) {...}` or a bare `export default function(...)` is recognized. Naming it `export function middleware(...)` inside `proxy.ts` silently fails to be picked up as the intended handler at all -- `handlerUserland` falls through to `mod.default`, which is `undefined`, and Next throws `ProxyMissingExportError: The Proxy file "..." must export a function named 'proxy' or a default function.` This is an easy mistake precisely because so much existing knowledge/muscle memory (and probably every StackOverflow answer and older tutorial) says `export function middleware`.

The `config = { matcher: [...] }` export is unaffected by the rename and works exactly as it always did in `middleware.ts`.

Also confirmed: Next detects and refuses to run if BOTH a `middleware.ts` and `proxy.ts` exist at the same convention level (repo root or `src/`) -- it throws at build time naming both paths and telling you to keep only the proxy one, rather than silently picking one.

Why this generalizes: this is Next.js 16's own framework-level file-convention change, not project-specific -- any Next.js 16 app migrating from `middleware.ts`, or starting fresh with `proxy.ts`, hits this exact export-name requirement.

##### How this is known

Read directly from `node_modules/next/dist/build/templates/middleware.js` and `node_modules/next/dist/lib/constants.js` (`MIDDLEWARE_FILENAME`/`PROXY_FILENAME` constants) in unitprep-ui's own installed Next 16.2.12, since the public docs migration guide didn't spell out the exact export-name fallback behavior. Verified end-to-end afterward: `proxy.ts` written with `export function proxy(...)` compiled and ran cleanly under `next dev` (Turbopack), with per-request timing breakdown showing `proxy.ts: Nms` in the dev server's own request log, and curl confirmed the gating logic (redirect-to-/login on a missing session cookie, pass-through with one present) worked correctly on every protected route.

## How this is known
