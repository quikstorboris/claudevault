# WSL npm install failures (EISDIR/EPERM on node_modules/.bin symlinks) mean npm is resolving to the Windows binary, not a WSL-native one

When running `npm install` for a project inside WSL (even one that genuinely lives on WSL's native ext4 filesystem, not /mnt/c) via `wsl.exe -d <distro> -- bash -lc '...'` from a Windows-side shell, repeated `EISDIR: illegal operation on a directory, lstat '\\wsl.localhost\...\node_modules\.bin\<pkg>'` or `EPERM: operation not permitted, rmdir '\\wsl.localhost\...'` errors during install/cleanup mean npm is not actually running as a native Linux process. Check with `which npm` / `which node` inside the WSL shell: if they resolve to `/mnt/c/Program Files/nodejs/...` (or similar), the WSL environment's PATH is pulling in the Windows-side Node.js install (via WSL's default Windows-PATH interop), and every node_modules/.bin symlink operation is crossing the 9P/drvfs bridge back into WSL from the Windows side -- exactly the boundary where Linux symlinks don't survive translation correctly.

Why this matters for a different project: this isn't project-specific -- it's a property of the WSL environment/PATH setup on this machine (or any machine with the same default WSL config), and will bite any npm-based project run this way, not just the one where it was first hit.

Fix: check for an existing native install first (`ls ~/.nvm/versions/node/` -- nvm is often already present even if not sourced in non-interactive `bash -lc` shells), then prepend it to PATH explicitly for the command: `export PATH="$HOME/.nvm/versions/node/<version>/bin:$PATH"` before running npm. Verify a candidate is genuinely native first with `file $(which node)` -- it should report `ELF 64-bit LSB executable ... GNU/Linux`, not resolve through `/mnt/c/...`. If no native node exists at all, install one inside WSL (nvm install, or a Linux Node.js package) rather than relying on the Windows install reached through interop.

Lightweight npm commands that only rewrite JSON (`npm version`, probably `npm audit fix` without new installs) can succeed fine even through the Windows binary, since they don't touch node_modules/.bin symlinks -- this failure mode specifically appears once `npm install` needs to create/remove binary symlinks, which is why it can look like the environment "was fine" until a real install is attempted.

## How this is known

Reproduced twice with npm resolving to /mnt/c/Program Files/nodejs/npm (both failed with EISDIR on node_modules/.bin symlinks during cleanup), then confirmed the fix by prepending ~/.nvm/versions/node/v24.18.0/bin (verified as a genuine ELF Linux binary via `file`) to PATH -- the same install completed cleanly in 28 seconds with zero errors.
